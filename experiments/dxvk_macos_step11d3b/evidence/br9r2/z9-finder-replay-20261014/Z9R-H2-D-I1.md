# Z9R-H2-D-I1 — WindowServer / I1 review

## Scope and disposition

Read-only review of the current Z9 collector, controller, safety helpers, target telemetry source, and the retained Z9 failure record. No Wine, Finder, or other graphics process was launched; the FG-Metal project was not modified.

**I1 guard: PASS by source inspection.** The current controller does not accept the historical Z9 internal-only tuple as I1. It requires a unique public all-window candidate and a unique same-PID / same-CG-ID candidate from the separate successful on-screen query. The exact same-query join ID must agree with that result, and the canonical precondition requires a stable public ID over the recent interval. If the join is absent, I1 fails closed.

**H2 execution ordering: BLOCKED pending reconciliation.** H2 says the dedicated Finder treatment window is created only after the actual replay’s 20-second canonical PRE. The checked-in Z9 controller still activates Finder at PRE+3 s, creates the window at +4 s, raises it at +5 s, and stages it at +6 s. Its frozen protocol document specifies the same sequence. The reviewed controller therefore does not implement H2’s stated action order as written.

## Evidence

### Direct target identity and public correlation

- Target telemetry is gated to the enabled target process whose Unix PID is the current PID and whose trace role is `target` (`experiments/dxvk_macos_step11d3b/trace_loader.mm:1373-1376`). The association code first accepts the direct delegate only when the delegate is an `NSView`, `view.layer == layer`, and `view.window` is non-null; it returns that exact view/window and marks lookup path 1 (`trace_loader.mm:1414-1427`). A bounded subtree fallback is separately marked path 2 (`trace_loader.mm:1401-1411`, `1429-1438`); the replay controller rejects anything other than `direct_delegate` (`z9_finder_replay.py:1343-1346`).
- Each target telemetry snapshot records the layer pointer, matched view pointer, lookup path, NSWindow object pointer, `windowNumber`, visibility, key/main, miniaturization, occlusion state, alpha, level, frame, and screen (`trace_loader.mm:1525-1589`). The serialized `window_telemetry` event includes those identities and state fields (`trace_loader.mm:1686-1738`). The separate layer configuration validates `WineMetalLayer`, the CAMetalLayer class, and the same layer pointer (`z9_finder_replay.py:1355-1359`).
- Internal identity stability uses the five-part tuple `(layer_id, window_view_id, window_lookup_path, window_id, window_number)`, requires positive layer/view/window/window-number identities and direct-delegate lookup, and requires a real two-second span with no gap over 1.5 seconds (`z9_replay_safety.py:384-430`). A changed tuple after acceptance is recorded as an identity change and sets an error (`z9_finder_replay.py:937-950`); `current_link` also rejects a changed tuple (`z9_finder_replay.py:1362-1363`).
- The collector queries `.optionAll` and `.optionOnScreenOnly` separately and records individual start/end bounds for each (`public_cgwindow_inventory_z9.swift:505-517`, `575-586`). It retains every row owned by the target PID from the all-window result in `windows` and every target-PID row returned by the on-screen query in `onscreen_windows`; it similarly retains same-Finder-PID rows (`public_cgwindow_inventory_z9.swift:520-559`, `587-599`). The query excludes desktop elements (`public_cgwindow_inventory_z9.swift:276-282`). Rows are a deliberate field projection—PID, CG ID, owner/title, bounds, layer, alpha, on-screen flag, and ranks—not the original unfiltered CGWindow dictionaries (`public_cgwindow_inventory_z9.swift:295-317`).
- `target_correspondence` finds exactly one all-window row matching replay PID, exact target title, telemetry-derived converted frame, AppKit level/CG layer, and alpha (`z9_finder_replay.py:387-408`). It then requires exactly one on-screen row with the same PID and CG ID, `onscreen == true`, the exact title and converted frame, plus the all-row `on_screen_joined` marker (`z9_finder_replay.py:409-418`). A missing on-screen join returns `UNIQUE_ONSCREEN_JOIN_FAILED`; no `window_number == CGWindow ID` shortcut can turn that into PASS.
- `current_link` additionally requires the same-query cover-evidence target ID to equal the correspondence ID (`z9_finder_replay.py:1293-1317`). During every newly-read public sample it computes the link, preserving the result, join status, same-query target ID, internal identity tuple, window number, and target row (`z9_finder_replay.py:922-972`, `1371-1399`).
- The numeric `window_number`/CG-ID equality is explicitly supporting runtime evidence, not an API identity contract; a mismatch is recorded as `MISMATCH_OR_UNAVAILABLE` while the primary public match basis remains PID, converted frame, title, layer, alpha, and a unique on-screen row (`z9_finder_replay.py:420-434`). The predeclared protocol makes the same qualification (`Z9-PREDECLARED-PROTOCOL.md:13`). Thus I1 is a strong unique runtime correlation, not a documented public API identity guarantee.

### Stable I1 and failure behavior

- For canonical PRE, recent public-link rows must all pass, both queries must have succeeded, the same-query target join and cover evidence must be complete and CLEAR, the same-query join ID must agree with the target correspondence, and one CG ID must persist. The public interval must span at least 2 seconds; recent sample-start gaps must all be at most 100 ms; and the latest query must be no older than 500 ms (`z9_finder_replay.py:1445-1476`). Canonical PRE also requires stable direct internal identity, fresh observer state, healthy renderer, on-screen target, state 8194 / Visible bit set, and CLEAR cover evidence (`z9_finder_replay.py:1477-1518`).
- The historical Z9 controller record demonstrates the intended fail-closed outcome: internal tuple `[105553143913888, 140628519379200, direct_delegate, 140628519331808, 2405]` remained stable, but the all-window candidate 2405 was not joined to the on-screen list, so the target correspondence was `UNIQUE_ONSCREEN_JOIN_FAILED`, public ID was null, and stable public identity was false (`experiments/dxvk_macos_step11d3b/evidence/br9r2/historical-closure-review/source-controller/timeline.jsonl:1`; summarized in `STEP-11D3-BR9R2-REPORT.md:867-871`). The final report correctly says replay-phase I1 was not established (`STEP-11D3-BR9R2-REPORT.md:909-910`). This is the exact historical condition that must remain a hard failure.

### Unrelated opaque full-window cover detection

- For a uniquely joined public target, the collector identifies rows in front of its on-screen rank. Any front row missing window ID, owner PID, positive bounds, or alpha makes cover evidence incomplete/UNKNOWN. A candidate full cover needs window alpha at least 0.999 and bounds containing the target; overflow also forces UNKNOWN (`public_cgwindow_inventory_z9.swift:105-143`, `144-161`). The resulting per-sample state is CLEAR only when the evidence is complete and no such row exists.
- The Python verifier rechecks that each cover row is well-formed, above the target, alpha >=0.999, and fully contains the target; it classifies an unexpected owner/ID as `UNEXPECTED_COVER` unless it is the exact allowed Finder identity (`z9_replay_safety.py:255-303`). The public query’s front-to-back rank is retained from the separate on-screen list.
- This proves public window-level alpha and rectangular containment, not opaque per-pixel content. The two CoreGraphics queries are sequential, not atomic; their begin/end bounds are retained. The prior independent review explicitly retained both caveats (`STEP-11D3-BR9R2-REPORT.md:758`). Desktop elements are excluded, so an excluded desktop element is not classified by this detector. It also tests each window’s full containment rather than unions of multiple partial windows. These are limits on the meaning of `CLEAR`/`COVERED`; do not describe the record as compositor-level or per-pixel proof.

### Finder identity controls

- Finder PID is obtained by exact process-name query `/usr/bin/pgrep -x Finder`; exactly one PID is required (`z9_finder_replay.py:236-242`). The collector records the Finder PID’s full row set in both query results before target handoff and throughout the target lifecycle (`public_cgwindow_inventory_z9.swift:357-399`, `388-439`, `540-599`).
- The replay captures the pre-creation same-PID Finder CG-ID set. After creating a uniquely named run-owned Finder folder/window, it requires exactly one new row for that title under the same Finder PID, absent from the pre-creation ID set, and exactly one matching on-screen row. AppleScript’s window ID is retained separately from the public CGWindow ID (`z9_finder_replay.py:1589-1608`, `1775-1865`).
- Before/after every later window action, source checks the current Finder PID, freshness and success of both query results, unique exact Finder PID/CG-ID/title row in the all-window set, unique title, matching layer/alpha, and exact on-screen row. Actions requiring front order compare the same on-screen sample’s Finder and Wine target ranks (`z9_finder_replay.py:814-890`, `1020-1085`). The AppleScript rechecks its own window ID and the unique target-folder name before mutation (`z9_finder_replay.py:1210-1220`); the AX raise is guarded by the same Finder PID/title and followed by a public front-order proof (`z9_finder_replay.py:1222-1288`). Full-cover proof requires the exact Finder PID, CG ID, title, and layer, alpha >=0.999, full containment of the fresh target rectangle, and front rank, with the same-query state identifying that exact cover as the only full-cover candidate (`z9_finder_replay.py:438-468`, `1980-2009`).
- Finder process identity is PID plus exact process name; source does not separately validate Finder’s bundle identifier, executable path, or code-signing identity. If H2’s phrase “correct Finder identity” requires executable-level authentication beyond a unique `pgrep -x Finder` PID, that check is absent.

## Cadence: request versus observation

- The controller passes `50` milliseconds (`z9_finder_replay.py:1551-1555`); the collector accepts intervals from 50–1000 ms and records `poll_interval_ms` and a start-to-start monotonic-deadline schedule that skips missed slots without catch-up (`public_cgwindow_inventory_z9.swift:332-345`, `479-491`). For each sample it records the scheduled deadline, actual sample start, inter-sample gap, missed-deadline count, and overall/per-query start/end/duration (`public_cgwindow_inventory_z9.swift:493-517`, `561-600`, `612-620`).
- This is a **requested 50 ms cadence**, not a guarantee of one observation every 50 ms. Query and serialization time, scheduler delay, and output I/O can cause skipped deadlines. The retained Z9 run had a 209.769375 ms maximum observed sample-start gap and a 155.210708 ms maximum query duration despite the 50 ms request (`STEP-11D3-BR9R2-REPORT.md:871`).
- The protocol’s actual coverage checks use observed data: canonical public identity needs <=100 ms gaps (`z9_finder_replay.py:1451-1476`), and a valid covered phase needs at least 350 samples, no query failures, and <=100 ms maximum gap (`z9_replay_safety.py:330-381`). A 50 ms request alone cannot establish either condition. The internal AppKit telemetry source is separately initial/event-triggered plus a 1.0 second main-run-loop timer with 0.1 second tolerance (`trace_loader.mm:1594-1644`, `1832-1854`); it is not sampled at 50 ms. Each public sample is correlated against latest telemetry only if the telemetry is fresh and within the existing 500 ms alignment bounds (`z9_finder_replay.py:1320-1337`).

## Exact gaps / actions for the orchestrator

1. **H2 sequence mismatch (execution blocker):** H2 explicitly says not to create the dedicated Finder treatment window before actual replay PRE and sets the measured sequence to 20 seconds uncovered, then 40 seconds cover, then 20 seconds restored. The current controller’s measured PRE itself schedules Finder activation/create/raise/stage at +3/+4/+5/+6 seconds (`z9_finder_replay.py:1694-1704`, `1731-1750`, `1877-1931`), matching the checked-in predeclared protocol (`Z9-PREDECLARED-PROTOCOL.md:19`) but contradicting H2. Reconcile and review a new protocol/controller binding before any live execution; do not treat the existing controller as compliant with H2’s later-only creation requirement.
2. **No direct unit test found for the critical regression guard:** `test_z9_replay_safety.py` tests the real two-second internal identity span and rejects sparse covered sampling (`:145-215`), but it does not exercise `target_correspondence`’s absent/duplicate/mismatched separate on-screen join branches. The source guard is present and the historical run demonstrates fail-closed runtime behavior, but a targeted pure-helper regression test would make this specific invariant durable before controller changes. No tests were run or added for this review.
3. **Window-number mismatch is non-fatal by design:** controller records it but public match may still PASS when the unique same-PID/title/geometry/layer/alpha candidate passes the separate on-screen join. Keep that declared interpretation; do not use window-number equality as a substitute join, and do not upgrade I1 to a platform-guaranteed identity claim.
4. **“Complete rows” means complete PID row set, not all public row keys:** all returned same-PID rows are retained, but each is projected to selected fields. If H2 requires raw per-row dictionary retention rather than retention of every same-PID row and the identity/geometry/rank properties needed here, current code does not do that.
5. **Cover proof has bounded semantics:** it detects a single preceding public window with alpha >=0.999 and containing bounds, with fail-closed treatment of unclassifiable preceding rows. It does not prove pixel opacity, model the union of partial covers, include desktop elements, or make the two WindowServer queries atomic.
6. **Cadence is not a coverage assertion:** report actual sample gaps and query bounds for the fresh attempt. If observed gaps violate the existing 100 ms qualification, the interval is incomplete; do not infer successful 50 ms sampling from the configured argument.

## Bottom line

The core I1 regression defense is correctly structured: stable internal identity is necessary but insufficient; I1 requires a contemporaneous unique public target joined into the separate on-screen result, with a stable public CGWindow ID. Historical Z9 failed that join and remains non-I1/R5. The H2 run should remain **NO-GO until its Finder-window timing requirement is reconciled with the current predeclared controller sequence**. Keep the known sequential-query, public-alpha, field-projection, and actual-cadence limits explicit in any later classification.
