# Z9R-H1 Subagent F — Historical Closure Adversarial Review

**Decision: NO-GO for implementation as currently sketched.** The semantic direction is viable only if the closure is an authenticated, exact-snapshot exception for this one terminal historical run, with mutation checks that cannot be rebased, and if the required process/lease and storage tests below pass. A list of certificate fields by itself is not a sufficient fail-closed contract.

## Scope and source map

This is a read-only adversarial design review. I did not run tests, invoke Gate 0, inspect or rewrite the historical run tree, change the original manifest or results, or perform any storage operation. I created only this review file. The historical run tree must remain untouched during implementation testing.

## Closure design assessment

The proposed fields cover useful provenance, but implementation must define and enforce all of these invariants before admitting a closure:

1. **Exact one-run authorization of the exception.** Require canonical run ID, exact storage-manifest path and raw SHA-256, exact run-manifest path and raw SHA-256, original 314,572,800-byte reservation, exact original Gate PRE/POST and cleanup/run-result hashes, and the original report/controller evidence that supports R5/T8. Reject ambiguity, duplicate IDs, missing records, noncanonical paths, and any mismatch. The signed storage manifest's HMAC and `decision=ALLOW` authenticate reservation data (`storage_policy.py:627–645, 1180–1195`); the closure must not silently replace or reinterpret it.
2. **Terminality is a live precondition, not a copied result field.** A recorded `timed_out=false` or empty Gate POST lease list does not prove there is no process still using the output or prefix. Refuse if the run is active, if process state is unknown, or if its target/runner process identity cannot be matched safely (PID reuse matters). Refuse any exact-run or ambiguous active PrefixLease and any active/ambiguous BuildLease. Existing Gate 0 has global active-marker and BuildLease checks, but there is no general historical-run process/output liveness API in the inspected closure path; `_pid_is_definitely_gone()` is a narrow PID check for recovery, not proof that no process has an output or prefix open (`storage_policy.py:2426–2435`).
3. **The exception must bind the current tree exactly.** Preserve the original Gate POST allocation (598,573,056 bytes) as a historical measurement and separately bind the current closure snapshot (the prior provenance report measured 725,688,320 allocated bytes). The original reservation and POST result stay unchanged. Never interpret the difference as a new reusable allowance. Accept only the exact closure snapshot; any added, removed, replaced, or altered entry must fail, even if the altered tree remains below 55 GiB and free space remains above 50 GiB.
4. **Make the snapshot race-safe and symlink-averse.** Do not use `_persistent_output_snapshot()` unchanged as the closure's proof: it does not hash content and it can record an already-present symlink as a normal tree row. Use descriptor-relative no-follow traversal, verify every opened file is regular and on the expected device, hash file contents, bind relative paths and root identity, and compare per-entry identity before/after reads. Take and compare the snapshot around durable closure creation under the storage certification/allocation serialization used by Gate 0. If any identity, digest, allocation, path set, or liveness state changes between samples, fail without installing an accepted certificate. Gate 0 must revalidate against this immutable closure on every invocation; a fresh preflight must not be allowed to overwrite the closure baseline after a mutation.
5. **Keep closure authority narrow.** Only the signed-output historical-overrun check may consume a verified closure, and only for the exact run ID and exact bound tree. It may not produce an `ALLOW` storage manifest, create or satisfy a PrefixLease, authorize a runner, change `decision`, or substitute for a current Gate 0 attestation. The current run paths require an authenticated `ALLOW` manifest and separately bind active lease, Gate 0 hash, and exact paths (`storage_policy.py:1523–1615, 3176–3235, 4925–4971, 5174–5222`). Test this separation at the actual runner/preflight boundary, not just by asserting a Boolean field in a certificate.
6. **Preserve failures and charge every byte.** The closure must not edit or rewrite either manifest, Gate PRE/POST, cleanup receipt, run result, controller result, or R5/T8 report text. The run and closure records and signed output remain in project inventory and the 50/55 scope calculations. Existing design correctly distinguishes full project allocation from the non-lease comparison total; closure must not broaden exclusions beyond this exact manifest/output pair (`storage_policy.py:2106–2206`; `test_storage_policy.py:424–453`). Keep the closure record outside the run-tree digest to avoid self-reference, but inside accounted project storage.
7. **Invalid closure evidence must block.** If a closure file is present but has the wrong signature, schema, run ID, manifest hash, tree identity, tool version/hash, or source-result hash, Gate 0 must emit a blocker. It must not treat a malformed certificate as if no closure existed and then rebase it as ordinary stable evidence. The normal signed-manifest scanner currently `continue`s past several malformed candidates (storage_policy.py:609–645); a closure path needs an explicit fail-closed contract.

As stated, the closure proposal does not yet specify the snapshot mechanism/atomicity, process-open detection, exact required source-record validation, append-only/no-replacement behavior, or the rule that Gate 0 may never rebase a closed tree. Those are safety properties, not optional implementation details. Therefore implementation should not begin until they are adopted as mandatory requirements. This is a NO-GO on the current sketch, not a rejection of a carefully bounded logical closure.

## Required adversarial and regression tests

Implement these as synthetic tests in the existing isolated-fixture style, primarily alongside `experiments/storage/test_storage_policy.py` and `experiments/storage/test_g0c_checks.py`. Do not use the actual historical tree as a writable test fixture. In particular, never add/remove/rename files beneath `experiments/dxvk_macos_step11d3b/runs/step11d3b-baseline-01-20261014-130823-44892b9b/` to test closure behavior. Use a temporary fake `REPO`, authenticated fixture manifests, fake Gate PRE/POST/result/report records, and a synthetic tree whose original reservation is deliberately smaller than its recorded output. Mock platform process/lsof and build-retention probes where necessary; optionally test a live held-open fixture file under `/private/tmp`, never a historical artifact.

## GO / NO-GO summary

**NO-GO before implementation on the proposal in its current form.** A separately authenticated historical-closure record is plausibly the smallest architecture-compatible direction because the existing signed-output scanner has no terminal run state and correctly blocks over-reserved output (`storage_policy.py:574–693`; `test_storage_policy.py:444–453`). But the proposed fields need the enforceable rules above, especially exact immutable snapshot binding, process and lease quiescence, symlink rejection, non-rebasability, and authorization isolation. The existing Gate 0 output identity comparison and whole-project accounting are useful building blocks (`storage_policy.py:1969–1981, 2052–2060, 2106–2206`; `test_g0c_checks.py:191–209`), not proof that the closure is already safe.

Re-review for GO only after the implementation plan explicitly includes every negative test in the matrix and the positive fixture proves that only the known historical overrun blocker is retired. The actual Z9 tree is evidence, not a mutation fixture; do not run adversarial writes against it. Before any eventual close on the real tree, independently record and compare the historical source hashes and a fresh no-follow inventory around the operation, then confirm the historical bytes remain in the current scoped allocation.
