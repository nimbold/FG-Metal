# Z9R-H1-C — Existing archive and retirement mechanisms

## Result

No existing FG-Metal mechanism closes a **run** as a terminal, non-authorizing historical record while leaving its signed run tree and original Gate result intact. The repository has physical archives for failed or superseded evidence, narrow raw-file retirement tools, PrefixLease recovery markers, and BuildLease retirement. Each has a different object and lifecycle contract. None can be reused as a Z9 run-closure record.

The target run is `step11d3b-baseline-01-20261014-130823-44892b9b`. Its signed manifest binds the original output directory and a 314,572,800-byte reservation ([manifest](../../../../storage/manifests/step11d3b-baseline-01-20261014-130823-44892b9b.json): lines 46–67). None of the existing archive allowlists names this run.

## Effects of physical archival on Z9

The target manifest is still a signed `ALLOW` record whose `output_dir` points to the expanded run directory and whose persistent reservation is 314,572,800 bytes ([manifest](../../../../storage/manifests/step11d3b-baseline-01-20261014-130823-44892b9b.json): lines 46–67). Gate accounting resolves that directory and fingerprints its directory/file identities and allocated bytes ([`storage_policy.py`](../../../../storage/storage_policy.py): lines 472–534, 656–693). The current attestation compares current historical-output bindings with its certified bindings and adds `signed historical experiment outputs changed since Gate 0 certification` when they differ (lines 1969–1981). Therefore moving bytes into a tar or removing raw files changes the signed output tree/path binding; the old attestation will detect that change.

There is no archive lookup or receipt-consumption path in the signed-output verifier. A missing output tree is measured as zero by `_persistent_output_snapshot` (lines 472–476), so physically moving the entire run into an archive would not, by itself, prove that the archived manifest/tree matches the missing signed output. Treating that zero as a retirement would require a new explicit contract; the current archive receipts do not supply it.

Project-scope accounting is filesystem-based. `storage_inventory.py` scans the main checkout and counts regular files by allocated inode bytes, with no archive exclusion ([`storage_inventory.py`](../../../../storage/storage_inventory.py): lines 30–45, 319–346). The BR6 `.tar.gz` example is counted as its actual allocated archive size in the saved inventory. Thus a retained in-repository tar remains charged for its allocated archive bytes, while deleted expanded files no longer contribute their former allocations. This can reduce scoped allocation through compression; it does not preserve the expanded run's charged allocation or inode/path identity. The existing BR8 plan likewise says not to credit archival savings before measuring the archive and refreshed inventory ([`storage-retention-plan.md`](../../br8/storage-retention-plan.md): lines 14–18, 26).

Per-file receipts can preserve content provenance across archival: repository-relative source path, archive member path, SHA-256, size, and pre-retirement device/inode metadata. Restoring a tar recreates file bytes and names, not the original inode identities. Existing reports and run JSON can still point to the original names, but those paths are absent until restore; the BR8 assessment documents this exact broken-link consequence ([assessment](../../br8/focus-control-retention-assessment.md): lines 33, 39–41). These properties are useful for optional storage reclamation, but they conflict with the Z9 requirement to keep the original signed output tree and its bytes in place and charged.

## Recommendation to the orchestrator

Use no physical archive or existing retirement tool for Z9. The only existing compatible parts are implementation patterns: exact run identity allowlists, no-follow filesystem checks, full hash/size inventories, append-only receipts, HMAC or other existing evidence sealing, and durable provenance. They do not implement the required logical meaning: “this exact run is terminal; preserve its original reservation and failed Gate evidence; no future execution is authorized.” If Gate 0 is to stop treating the known failure as unresolved, a run-level closure state must be added and verified explicitly while the original run directory remains at its manifest-bound path. That is a new primitive, not reuse of the archive lifecycle.
