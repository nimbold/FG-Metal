# Z9R-H1-E — Accounting and storage consequences

**Scope:** read-only review of storage source and saved measurements for the historical run `step11d3b-baseline-01-20261014-130823-44892b9b`. No Gate operation, test, inventory refresh, or experiment was run. This report is the only file created by this workstream.

## Finding

A logical closure can remove exactly the known historical reservation-overrun blocker while preserving the run's bytes and failure history, but only if Gate 0 continues to account for the complete tree and binds its exact closed snapshot. The closure must not enlarge the old reservation, credit the bytes out of scope, or waive any other blocker. A blanket exception or dropping this run from the signed-output snapshot is unsafe.

## Answers to the six accounting questions

### 1. Do the historical bytes remain in scoped project allocation?

**Yes.** The complete current Z9 tree remains charged. `measure_project_usage()` always computes the whole-project allocated-inode total; an exclusion produces only a separate comparison subtotal, and hard-linked inodes with links outside an excluded tree remain included ([`storage_policy.py`, lines 2106–2112 and 2185–2205](../../../../storage/storage_policy.py#L2106-L2112)). The source's persistent-output snapshot documents the same rule: eligible outputs remain in whole-project allocation and are excluded only from unrelated-growth comparison ([lines 574–584](../../../../storage/storage_policy.py#L574-L584)). The inventory scan also continues to include the run files; no output reservation is subtracted from `fgmetal_scoped_allocated_inode_bytes` ([inventory implementation, lines 403–429](../../../../storage/storage_inventory.py#L403-L429)).

The closed tree's measured **725,688,320 bytes** therefore remains in current scope, projected scope, and inventory. The closure record and review report are also project bytes and must be counted. Any final admission must use the refreshed whole-scope measurement, not a scope value with Z9 removed.

### 2. Is the old reservation rewritten?

**No.** Keep the signed storage manifest at **314,572,800 bytes** and byte-identical. The 4,974,444,544-byte future reservation is for a later run only. Closure may classify the measured overrun as a known terminal historical exception for Gate accounting; it must not call that overrun within-reservation, change the old reservation, or imply retroactive admission. This distinction follows the existing blocker's direct comparison against the manifest reservation ([`storage_policy.py`, lines 677–692](../../../../storage/storage_policy.py#L677-L692)).

### 3. Does the overrun remain visible in audit and reporting?

**Yes.** Preserve the original reservation, Gate POST failure, POST/current allocations, and R5/T8 classification as separate historical facts. The report should continue to state that the 598,573,056-byte POST tree and 725,688,320-byte later tree exceeded the original 314,572,800-byte reservation. A closure may add a signed explanation of why Gate 0 can now account for this terminal tree; it must not replace the overrun values with a new cap or erase the original blocker from the historical result. The prior failed Gate record itself is explicit in the blocked attestation's `gate0_blockers` field ([attestation, lines 44–46](../../../../storage/storage-gate0-attestation.json#L44-L46)).

### 4. What should stop blocking future Gate 0?

Only this exact unresolved condition should stop blocking: `signed experiment output exceeds its persistent reservation` for this exact run ID, after Gate 0 validates an append-only, authenticated closure that binds the terminal run, original manifest hash and reservation, original Gate POST failure, and current surviving-tree snapshot. The current code has no terminal-run exception: it skips an over-reservation output from both `bindings` and `output_paths` and emits the blocker ([`storage_policy.py`, lines 574–584 and 677–693](../../../../storage/storage_policy.py#L574-L584)). The current persisted Gate 0 attestation records that same blocker ([lines 44–46](../../../../storage/storage-gate0-attestation.json#L44-L46)).

Closure should let the exact closed output return as a **fully bound historical output** for comparison accounting, without declaring its allocation to fit the reservation. Gate 0 must still reject malformed/stale closure evidence, changes to the old manifest or POST record, any other overrun, unrelated nonlease growth, scope above 55 GiB, projected free below 50 GiB, and active leases. The existing policy thresholds are 50 GiB minimum projected free, 55 GiB scope ceiling, and the unchanged warning/preferred levels ([`storage_policy.py`, lines 38–49](../../../../storage/storage_policy.py#L38-L49)).

A closure should make only that one exact historical overrun eligible for the bound-output comparison treatment.

### 6. Could closure hide future mutation inside the historical tree?

**Yes, if closure simply drops Z9 from the output snapshot or permanently ignores its path.** That would hide added files and could mask manifest edits or path replacement from the signed-output identity comparison. It would also turn the closure into an unbounded storage allowance.

**A fail-closed closure does not hide mutation.** Bind the closure to the exact experiment ID, original manifest digest and immutable reservation, output-root device/inode, a canonical relative-path inventory, file-content digests, allocated byte totals, and required critical-artifact hashes. At every Gate check, require the current snapshot to match exactly; reject unexpected files/bytes, changed content or identity, missing required artifacts, and symlink/non-regular substitutions. Take and recheck the snapshot around accounting so mutation during the scan fails closed. If it differs, do not return the Z9 root as an exclusion and do not refresh the nonlease baseline.

The existing persistent-output guard records device, inode, mode, owner, link count, size, mtime, ctime, and block allocation and compares a second snapshot around Gate 0 ([`storage_policy.py`, lines 464–534 and 2052–2060](../../../../storage/storage_policy.py#L464-L534)). Its output-tree digest is an identity/metadata digest; it does not hash file contents. A closed-run certificate should therefore add a safe content-hashed relative-path inventory, using no-follow regular-file reads with before/after descriptor identity checks, rather than treating the existing metadata digest alone as the closure's content proof. The repository has a content-hash helper for tree entries, but it follows ordinary `Path.open()` after `lstat` and has no descriptor-bound readback in this helper ([`storage_policy.py`, lines 2209–2256](../../../../storage/storage_policy.py#L2209-L2256)); it is a pattern to harden, not sufficient by itself for this trust boundary.

## Fail-closed accounting design

**Design conclusion: GO for evaluating a narrow terminal-closure primitive; NO-GO for any implementation that raises the old reservation, deletes/moves the tree, suppresses all historical-output checks, or rebases away project growth.** Gate 0 may stop blocking solely on the known reservation overrun only after validating an exact non-authorizing closure and the frozen tree snapshot. It must continue charging the current tree and closure evidence to the full project total, continue enforcing projected 55/50 limits, preserve the old overrun in audit/reporting, and fail on any subsequent tree or unrelated-storage mutation. The present saved inventory/attestation cannot supply a valid current nonlease baseline; that baseline must be re-established only after successful closure validation and a fresh complete storage inventory.
