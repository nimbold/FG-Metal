# BR8 externally controlled inactive-app repeat: independent assessment

## Finding

The accepted run `step11d3b-br8-state-02-20261011-005208-590fa5da` establishes a controlled target foreground → inactive → foreground sequence while the target window stays visible, ordered, and nonminiaturized. It is a valid negative result for this 40-second inactive-app hold: target telemetry remains inactive/nonkey/nonmain with AppKit's visible bit set, and presentation stays near 60 Hz. The target returns to main/key/active state at the +60-second action, with the first 10 seconds after key restoration at 60 acquired and displayed FPS. The run does not establish that the inactive state can never affect presentation or resolve the BR6 cause.

## Controller semantics versus the old proxy mutation

The new controller uses `ApplicationServices` Accessibility APIs out of process. It creates an AX application element for the selected PID, confirms a unique expected window title, checks that application-level `AXFrontmost` is settable, and calls `AXUIElementSetAttributeValue` on that application element. For all three actions in this run, the settable check returns true and `action_error=0`. The action helper identities in [controller-identities-frontmost-final.json](controller-identities-frontmost-final.json) match the current files reviewed (`state_sequence.py`, `ax_window.py`, `coverage_snapshot.py`, and `window_sequence.py`). Target-owned notifications establish the actual state transitions; CG ranks establish the external order. The AX setter's success by itself is not treated as attainment, and the action log remains a separate chronology from target telemetry.

This control changes OS-level app-frontmost state intentionally. It does not change target proxy code, inject into Wine, or set `CAMetalLayer` properties. The preserved BR6 proxy had a broader in-process one-time behavior: it could repair `drawableSize` when either dimension was invalid, set the app activation policy and activate it, then change level and hide-on-deactivate state and make/order every app window front. That historical mutation is not equivalent to this one application-level AX request; the current run isolates an externally requested foreground-state transition more cleanly, while still allowing the expected activation and window-order consequences. It does not show which individual BR6 setter caused the historical pathology. See the original [BR6 proxy source](../br7/trace-loader-br6.mm) and the [BR6-to-BR7 source review](proxy-diff-review.md).
