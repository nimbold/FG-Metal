# BR8 proxy source behavioral diff: BR6 vs BR7

## Scope and identity

This is a read-only, source-level comparison of the preserved BR6 proxy source `experiments/dxvk_macos_step11d3b/evidence/br7/trace-loader-br6.mm` and the BR7 passive source `experiments/dxvk_macos_step11d3b/trace_loader.mm`.

- Preserved BR6 source SHA-256: `c6bbc3c34c6b5708ae231946ccfe4c8ab9ed270519454d6a9f1819209a4bea26`.
- BR7 source SHA-256: `75bde644c82d807fbb8c0ee01878ffa24a8f3c75e1997345ea4a4a95ab8c65b3`; it matches `evidence/br7/proxy-build.json` (`source_sha256`). The recorded BR7 build output SHA-256 is `bdd1d742687f54bfba806c8d126e889fb4958fdbe15dcca10ac324103564e131`.
- The BR6 report records the accepted proxy binary SHA-256 as `1b3dda059905bbacb6dfb63718c78eb1505682fb6d493d5be2ef4dec51a38688` (`STEP-11D3-BR6-REPORT.md:78`). This identifies the binary, while this review compares the preserved source snapshot to the BR7 build input.
- The unified diff has five hunks: CoreGraphics import; telemetry state and forward declaration; the first-`nextDrawable` hook call; and replacement of the single mutating configuration function with a read-only identity/configuration path plus window observation. Outside those hunks the source is unchanged. Existing Vulkan wrappers, drawable/present/dealloc interposition, and layer-method patching remain the same.

**Finding:** BR6 was not presentation-passive. On its one-time configuration path it could assign `CAMetalLayer.drawableSize`, activate the app, and reorder/change every app window. BR7 removes those writes and instead records state. BR7 is passive with respect to AppKit window state and layer presentation properties, but it is not timing-neutral: it adds main-queue work, AppKit observers, a repeating timer, state reads, event serialization, and logging. BR7 runs therefore are not exact old-proxy repeats. This matches BR7's correction of the BR6 manifest claim at `STEP-11D3-BR7-REPORT.md:5`.

## Trigger, ordering, and thread

**BR6:** A successful `vkCreateMetalSurfaceEXT` invokes `emit_layer_configuration` synchronously after the delegate returns and before the wrapper records surface completion (`trace-loader-br6.mm:1081-1097`). If that path does not emit, the first `WineMetalLayer.nextDrawable` call invokes the same function synchronously before calling the original method (`1241-1249`). One `g_layer_config_emitted` atomic gates the whole operation (`1303-1305`). The layer inspection and possible size write run on the thread calling the wrapper. The AppKit changes are queued asynchronously to the main queue by that same first invocation (`1313-1326`); their execution order relative to swapchain creation or the blocked first drawable is not guaranteed.

**BR7:** The successful surface hook still emits an early layer identity record synchronously (`trace_loader.mm:1141-1158`, `1702-1728`), before swapchain creation. That record has its own one-time guard and no longer consumes `g_layer_config_emitted`. The first `nextDrawable` hook separately calls `start_window_observation` (`1301-1309`). That method atomically claims the one-time observation setup, then queues a main-queue block before invoking the original `nextDrawable` (`1730-1779`). The block may run while the original call is still blocked; it is not guaranteed to run after drawable return (`evidence/br7/lifecycle-split.md:5`). AppKit/window snapshot reads and notifications are confined to the main queue: non-main callers are re-queued by `emit_window_telemetry` (`1564-1572`), and timer/notification callbacks also execute on main (`1595-1634`, `1763-1776`).

The telemetry path is explicitly gated to an enabled target process whose PID and role match (`trace_loader.mm:1363-1367`, `1730-1737`). The BR6 configuration function had no corresponding target-role/PID guard; it was reached from proxy Vulkan/layer hooks (`trace-loader-br6.mm:1081-1097`, `1241-1247`). Thus BR7 also narrows observation to the designated target process, while BR6's one-time side effects could occur in any process that reached those hooks.

## AppKit and NSWindow behavior

**BR6 writes:** Once per proxy process, its queued main-thread block sets the app activation policy to regular, requests activation while ignoring other apps, and loops over **all** `NSApp.windows`. For each window it sets normal level, disables hide-on-deactivate, makes it key and orders it front, then orders it front regardless (`trace-loader-br6.mm:1313-1326`). This is not limited to the Vulkan target window. It can change foreground activation, key/main selection, z-order/visibility, level, and deactivation behavior. In a multi-window app, iteration may leave a different window key/front than before.

**BR7 reads/observes:** No corresponding setter or activation call exists in the BR7 source. It resolves the window associated with the observed layer through its `NSView` delegate or a bounded content-view-tree search (`trace_loader.mm:1391-1419`). On main it reads app-active, window visibility/key/main/occlusion/miniaturized state, alpha, level, frame, screen and backing properties (`1500-1562`). It registers app activation/resignation notifications and notifications for the associated window's move/resize/screen/backing/occlusion/miniaturize/key/main/close transitions (`1595-1634`), then emits initial, event-triggered, and one-second snapshots (`1637-1699`, `1763-1776`). If association is unavailable, it records that as unknown rather than selecting another window.

These reads and observers do not themselves activate, order, resize, raise, or de-miniaturize a window. They do add main-run-loop and trace work. `window_ordered` in the emitted record is populated from `isVisible`, not a separate ordering mutation or independent ordering observation (`1525-1526`).

## CAMetalLayer behavior

**BR6 conditional write:** At the one-time emitter, if **either** `drawableSize` dimension is nonpositive, BR6 chooses `contentsScale` or `1.0`, chooses each bounds dimension or fallback `640`/`360`, multiplies both by the scale, and assigns the resulting two-dimensional `drawableSize` (`trace-loader-br6.mm:1303-1312`). Because it assigns both dimensions, one invalid component can replace the other component even when that component was already positive. This can repair a zero/invalid drawable extent before swapchain creation, or at the first-draw fallback. It is the only CAMetalLayer setter found in the BR6 source diff.

**BR7 read-only split:** The early identity emitter reads raw class/image identity, drawable size, bounds, contents scale, pixel format, drawable count, timeout/sync flags and framebuffer-only state (`trace_loader.mm:1702-1728`). The separate first-draw observation reads the same presentation configuration plus hidden/opaque/masks-to-bounds (`1500-1519`, `1743-1762`), followed by periodic/notification snapshots. The BR7 source contains no `drawableSize` assignment and no setter for `displaySyncEnabled`, `maximumDrawableCount`, `allowsNextDrawableTimeout`, pixel format, framebuffer-only state, layer bounds, hidden/opaque state, or presentation mode. The added refresh-rate query uses cached public CoreGraphics display-mode data (`1421-1446`); it does not set a display mode.

Consequently, BR7 preserves the app/Wine-provided extent and flags as observed, including a nonpositive size if one occurs. It does not reproduce BR6's conditional geometry repair. A BR7 validation requirement for the observed layer to be 640×360 is a measurement/admission check, not a source write (`STEP-11D3-BR7-REPORT.md:78`).

## Presentation eligibility and causal limits

BR6 directly changes two classes of state that can affect presentation conditions: it conditionally forces a drawable extent, and it foregrounds/orders windows while changing their level and hide-on-deactivate behavior. Those actions can affect whether drawables are available and whether a window is visible/eligible for compositor presentation. They do **not** prove that BR6's pathological callbacks were caused by those actions, nor that key/main/active state is required for Vulkan submission. BR6 has no window telemetry, so its missing trigger state cannot be recovered retrospectively.

BR7 no longer normalizes those conditions. It observes active, visible, key/main, occlusion, miniaturization, geometry, screen intersection and layer flags, alongside the same existing frame/presentation instrumentation. The source and BR7 report do not justify assigning a zero `presentedTime` to `WINDOW_NOT_PRESENTABLE`, supersession, or a particular AppKit state. BR7 explicitly treats those as unassigned causes and notes callback-time state can postdate acquisition/request (`STEP-11D3-BR7-REPORT.md:66`, `147`, `160`). Its telemetry is useful for correlating transitions in a new run, not for proving BR6's historical trigger.

## Instrumentation overhead and unchanged presentation controls

BR7 adds one CoreGraphics include (`trace_loader.mm:11`), retained weak tables, snapshot state, notification tokens, and an `NSTimer` (`99-160`). It traverses the view tree (bounded at 4,096 views/depth 64), reads window/screen/layer properties, computes/serializes telemetry, queries display mode when needed, and writes trace records (`1391-1419`, `1425-1446`, `1500-1699`). The timer runs every second with 0.1-second tolerance in common run-loop modes (`1763-1775`). This activity can perturb main-thread scheduling and measurement timing even though it does not directly alter presentation properties. BR7's own report correctly says the telemetry sample is observational, not a guarantee of state between samples (`STEP-11D3-BR7-REPORT.md:76`, `160`).

The existing `nextDrawable` interposition still calls the original method and records begin/end timing; existing drawable presented-handler/dealloc instrumentation remains unchanged. This source diff does not change requested FIFO mode, swapchain image count, layer display-sync/timeout flags, pacing, or MoltenVK behavior. The accepted BR6 configuration was FIFO, three images, and a 640×360 CAMetalLayer (`STEP-11D3-BR6-REPORT.md:90`); BR7 states those controls were not changed (`STEP-11D3-BR7-REPORT.md:78`, `170`).

Separate from this proxy-only diff, BR7 also records that the old smoke screenshot helper activated the app, while BR7 screen capture does not (`evidence/br7/working-notes.md:7`, `STEP-11D3-BR7-REPORT.md:164`). That runner behavior is outside the two source files compared here and should be treated as a separate BR6 smoke confound; it does not alter the BR6 accepted baseline source diff described above.

## Phase A implication

Freeze the BR7 source by its recorded digest before Phase A and do not use BR6 activation/window writes or drawable-size repair. Keep any captures non-activating. Record the built proxy digest with the run. Classify any BR8 change only as an observed state transition correlated with an outcome unless an independent controlled repeat supports a trigger; this source diff alone cannot establish causation.
