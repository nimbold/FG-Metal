# Step 11B Subagent 2 — Runtime Vulkan/MoltenVK identity

Audit scope: read-only inspection of the Step 11A Wine runtime, its manifests and probes. No Wine process was launched and no runtime file was changed for this audit. The separately reported direct `dlopen` checks and Wine startup logs are used as runtime observations.

## Finding

**VERIFIED:** Step 11A compared two different Vulkan implementations while treating the names as if they described one loader path. The x86_64 Wine D3D11 lane reports MoltenVK 1.4.1 / Vulkan 1.4.334. Direct `dlopen` of the runtime's x86_64 host library, `/tmp/fgmetal-dxvk-macos-audit-run/runtime/wine/lib/wine/x86_64-unix/libvulkan.dylib`, reports `driverInfo=1.4.1`; its SHA-256 is `1d57a14b4a0d380420ab566884018fd83ba57381aa44e464f79472a77273b6bc`. This file matches the Wine lane's startup version. The original Wine PID's dyld image list was not captured, so exact in-process path tracing remains unavailable.

The runtime separately contains the ICD payload `/tmp/fgmetal-dxvk-macos-audit-run/runtime/wine/lib/wine/x86_64-unix/libMoltenVK.1.dylib`, SHA-256 `8249d81ebf2d46f82b16ca166c2e5cca5d76d91d0a412cd6d3db1aaa6e8430bf`. It is universal x86_64+arm64, and direct probes resolving this file report MoltenVK 1.4.3 / Vulkan 1.4.357 / `driverInfo=1.4.3`. This was the payload exercised by the standalone native probe, not the old `libvulkan.dylib` payload Wine used.

The mismatch is **not** explained by one universal binary carrying different versions in its slices, nor by stale `driverInfo` alone. The two relevant files have different hashes and different runtime-reported versions. The package includes a legacy `libvulkan.dylib` path alongside a newer ICD `libMoltenVK.1.dylib` path. The Step 11A direct probe took the latter route; Wine took the former.

**Additional live negative-control replay:** `evidence/negative-old-hud-10s/runtime.log` records dyld PID 90045 loading both `/private/tmp/fgmetal-dxvk-macos-audit-run/runtime/wine/lib/wine/x86_64-unix/winevulkan.so` and `/private/tmp/fgmetal-dxvk-macos-audit-run/runtime/wine/lib/wine/x86_64-unix/libvulkan.dylib`. That process reports MoltenVK 1.4.1 / Vulkan 1.4.334 and later reproduces the `DrawIndex is not supported in MSL` pipeline failure. The paths resolve to the preserved negative-control runtime files inventoried below. This is a **current replay** against the preserved Step 11A runtime and a copied test prefix; it is not a dyld trace from the original historical Step 11A PID. It closes the live-path gap for the replay without retroactively claiming original-PID capture.

## Loaded paths and resolution

- **Wine/DXVK:** The original Step 11A startup log reports 1.4.1 / 1.4.334. In the current negative-control replay, dyld explicitly records the exact bundled `runtime/wine/lib/wine/x86_64-unix/winevulkan.so` and `libvulkan.dylib` paths; that process reports the same 1.4.1 / 1.4.334 and reproduces the DrawIndex error. The old `libvulkan.dylib` file hash and direct `dlopen` result (`driverInfo=1.4.1`) match. `winevulkan.so` has no Mach-O load command for MoltenVK; the bridge obtains/uses Vulkan entry points through Wine's Vulkan provider. The original Step 11A PID's dyld image list remains **NOT AVAILABLE**; the replay's exact loaded path is **VERIFIED**.
- **Native linked probe:** `/tmp/fgmetal-dxvk-macos-audit-run/mvk_probe` is x86_64 and loads `@rpath/libMoltenVK.dylib`; its LC_RPATH is `runtime/wine/lib/wine/x86_64-unix`. The symlink there resolves to `libMoltenVK.1.dylib` (hash above). Probe output reports 1.4.3 / Vulkan 1.4.357.
- **Native loader probe:** `/tmp/fgmetal-dxvk-macos-audit-run/mvk_probe_loader` is x86_64; it loads the install name `@rpath/libMoltenVK.1.dylib` and uses the same x86_64-unix RPATH. Filename resolution selects the separate `libMoltenVK.1.dylib` (1.4.3), not `libvulkan.dylib`. Its output likewise reports driverInfo 1.4.3.
- **Manifest probe:** the Step 11A JSON record names `/runtime/wine/lib/moltenvk-vkmt/libMoltenVK.dylib`; that regular file has the same 1.4.3 hash. The manifest path and direct probe therefore do not identify the library used by Wine's D3D11 run.

This also corrects an `otool` interpretation in the Step 11A report: for `libvulkan.dylib`, `otool -L` prints its own `LC_ID_DYLIB` as the first line. That line is not a dependency edge to a second MoltenVK file. `otool -l` shows the actual `LC_LOAD_DYLIB` list, which contains only Apple frameworks/system libraries.

## Impact on the DrawIndex hypothesis

The Step 11A error occurred in the Wine lane running the 1.4.1 provider, while its successful direct Vulkan/Metal capability probe ran against the separate 1.4.3 ICD file. Therefore that probe did not test the failing Wine renderer. This makes the proposed “1.4.2+ may fix DrawIndex” explanation materially better grounded than it was, but it is still only a hypothesis until a direct DrawIndex pipeline A/B uses the exact 1.4.1 and pinned 1.4.2 payloads, followed by unmodified DXVK on the new Wine candidate.

**VERIFIED:** distinct runtime payload hashes; architecture slices; install names and dependencies; both ICD manifest targets; native 1.4.3 probe result; Wine 1.4.1 startup result; direct `dlopen` identity; and the exact `winevulkan.so` and `libvulkan.dylib` dyld paths from the current old-runtime negative-control replay.

**SUPPORTED INFERENCE:** Wine's D3D11 process reached the old `libvulkan.dylib` implementation through the Wine Vulkan bridge. This is supported by the Wine startup version and same-file direct `dlopen` result. The original Wine PID's dyld image list was not captured.

**NOT TESTED by this identity audit:** whether replacing only `libvulkan.dylib` or selecting the 1.4.3 ICD route is compatible and sufficient for DXVK; whether 1.4.2 fixes the DrawIndex shader; sustained D3D11 rendering under a corrected runtime.
