# Independent bookkeeping review

Reviewed `/tmp/fgmetal-dxvk-macos-audit-20261004` at `8d348236e14a3db25ffbe528a83010b3dd69a3ef`. The existing audit is accurate on the central coupling: D3D11 `m_frameId` is exposed as the app present count, passed through the queued present into Presenter WSI IDs, and also keys the Presenter frame queue, timing feedback, and completion fence. `GetFrameStatistics` reads the Presenter's single latest feedback record. `signalFrame` and the frame worker share `m_lastSignaled` / `m_lastCompleted`; `SyncFrameLatency` waits and registers callbacks in the D3D11 count domain, while `CallbackFence` releases callbacks whose target is at or below the value it receives. Source evidence: `src/d3d11/d3d11_swapchain.cpp:343-357,411-480,494-529,712-720`; `src/dxvk/dxvk_presenter.cpp:180-186,214-254,265-306,337-352,1558-1681,1989-2048`; `src/util/sync/sync_signal.h:32-40,148-190`.

The app ID increments after WSI acquire and CPU-side present setup, immediately before the source blit is enqueued; the copy itself runs later on the command-stream thread. Failed acquire and pre-enqueue validation paths do not increment it. Source backbuffer rotation occurs after enqueue, while WSI image/semaphore-ring advance and eager reacquire occur in `Presenter::presentImage` only when `vkQueuePresentKHR` returns a nonnegative status. These boundaries support separate app and WSI IDs and the proposed single WSI owner.

One nuance to tighten in the audit wording: NV Low Latency 2 markers do not generally reuse the WSI `frameId`. Reflex maps app frame IDs to its own tracker IDs; queue tracking and `DxvkCommandSubmission::submit` use those tracker IDs for NV submissions, and Presenter marker calls receive them. The existing audit's Reflex paragraph recognizes this distinction, so the broader “same ID … latency calls” finding should be read as shared app-ID plumbing, not literal NV-ID equality. Keep this mapping source-only and define its mapping to any new WSI ID explicitly. Evidence: `src/dxvk/dxvk_latency_reflex.cpp:23-40,270-310,439-483`; `src/dxvk/dxvk_queue.cpp:159-183`; `src/dxvk/dxvk_cmdlist.cpp:58-87`.

Failure-path qualification: D3D11 queues `DxvkDevice::presentImage` with a null `DxvkSubmitStatus`, so the later `vkQueuePresentKHR` result is not returned as that call's DXGI HRESULT. The frontend has its own acquire/validation HRESULT paths and Presenter recreation behavior. Preserve those observed semantics, but do not assume a low-level asynchronous present failure can be mapped back to the already-returned source `Present` result. Evidence: `src/d3d11/d3d11_swapchain.cpp:435-455,524-529`; `src/dxvk/dxvk_device.cpp:604-625`; `src/dxvk/dxvk_queue.cpp:170-184,283-288`.
