# Step 11B read-only audit — DXVK built-in shader and MoltenVK upgrade safety

**Pinned DXVK source:** `metalsharp/DXVK-MacOS` at `8d348236e14a3db25ffbe528a83010b3dd69a3ef`  
**Scope:** source and generated-SPIR-V audit plus isolated MoltenVK-upgrade design. No DXVK, Wine, MoltenVK, or test source was modified.

## DXVK shader trace

The normal D3D11 presentation path is:

1. `D3D11SwapChain::PresentImage` acquires a Presenter image and queues a command-stream callback ([d3d11_swapchain.cpp](/private/tmp/fgmetal-dxvk-macos-audit-20261004/src/d3d11/d3d11_swapchain.cpp:411)).
2. That callback calls `DxvkSwapchainBlitter::present` to draw the application backbuffer into the acquired Vulkan WSI image, then submits and presents it ([d3d11_swapchain.cpp](/private/tmp/fgmetal-dxvk-macos-audit-20261004/src/d3d11/d3d11_swapchain.cpp:516)).
3. The ordinary blit pipeline is created in `DxvkSwapchainBlitter::createBlitPipeline`; its vertex module is the generated `dxvk_present_vert` module ([dxvk_swapchain_blitter.cpp](/private/tmp/fgmetal-dxvk-macos-audit-20261004/src/dxvk/dxvk_swapchain_blitter.cpp:717)).

`dxvk_present_vert` is generated from `src/dxvk/shaders/dxvk_present_vert.vert` by the build rule invoking `glslang --target-env vulkan1.3 --vn dxvk_present_vert`. The captured module `/tmp/fgmetal-dxvk-macos-audit-run/dxvk_present_vert.spv` disassembles to an `OpDecorate ... BuiltIn VertexIndex`; it contains no `DrawIndex` decoration. Its SHA-256 is `20944398d1065cd783d1b652a93a7cf8b72ce66a7475fa18f31188ed01c3d9a7`. `spirv-val --target-env vulkan1.3` accepts it with status 0. The shader uses `gl_VertexIndex` to produce a three-vertex full-screen triangle, and the blitter issues `cmdDraw(3, 1, 0, 0)`. This is valid Vulkan SPIR-V and its VertexIndex use is intentional.

The exact error text is specifically associated with an SPIR-V `DrawIndex` built-in, but the source log only says “Vertex shader function” and the DXVK exception only says “built-in graphics pipeline.” `createBuiltInGraphicsPipeline` is shared by several internal paths and reports no shader name. Therefore the captured log does **not** prove that `dxvk_present_vert` was the failing module. A direct minimal-pipeline run of that exact module on the old loader/MoltenVK lane succeeded (reported by the parent task); that further argues against attributing the old MoltenVK failure to this ordinary presentation vertex shader. The actual failed module or pipeline specialization was not captured in 11A.

The only pinned DXVK shader source found that explicitly uses `gl_DrawID` is the optional HUD text vertex shader, `src/dxvk/hud/shaders/hud_text_vert.vert`. Its generated header is built with the same Vulkan 1.3 glslang rule. Disassembly of that generated SPIR-V shows `OpCapability DrawParameters`, `BuiltIn DrawIndex`, and `BuiltIn VertexIndex`. `gl_DrawID` selects `draw_infos[gl_DrawID]`, the per-text-draw record; `gl_VertexIndex` selects one of six vertices per glyph. `HudRenderer::flushDraws` writes one `VkDrawIndirectCommand` and one metadata record per text item, then calls `vkCmdDrawIndirect` with `drawCount` equal to the item count ([dxvk_hud_renderer.cpp](/private/tmp/fgmetal-dxvk-macos-audit-20261004/src/dxvk/hud/dxvk_hud_renderer.cpp:115)). That is the intended Vulkan DrawIndex/DrawParameters use. DXVK creates this pipeline only when the HUD has an enabled item. D3D11's HUD is sourced from `DXVK_HUD` or config and `CreateBlitter` adds the API/latency items only when that HUD exists ([dxvk_hud_item.cpp](/private/tmp/fgmetal-dxvk-macos-audit-20261004/src/dxvk/hud/dxvk_hud_item.cpp:27), [d3d11_swapchain.cpp](/private/tmp/fgmetal-dxvk-macos-audit-20261004/src/d3d11/d3d11_swapchain.cpp:676)).

MoltenVK's upstream 1.4.2 release notes explicitly add macOS `gl_DrawID` / `DrawIndex` support and say SPIRV-Cross was updated with that MSL support ([MoltenVK What's New](https://github.com/KhronosGroup/MoltenVK/blob/main/Docs/Whats_New.md#moltenvk-142)). This makes 1.4.2 the right minimum runtime version to test for a DXVK HUD-enabled path. The direct explicit-DrawIndex A/B probe separately reproduces `VK_ERROR_INITIALIZATION_FAILED` on the old lane, according to the parent task. That proves the runtime limitation, but not which shader triggered 11A.

The new-runtime debug run now provides positive evidence for the HUD path: `experiments/dxvk_macos_step11b/evidence/waitable-debug-30s/runtime.log` dumps a `hud_text_vert` module at lines 11786–11880 with `BuiltIn DrawIndex`, then MSL at lines 12236–12244 reads `spvDrawIndex` and indexes `draw_infos`. The 1.4.2 candidate translates and compiles that shader without the 11A conversion error. This validates the new driver's required capability on the actual DXVK HUD shader. It still does not identify the 11A failing shader by itself, since that old run's pipeline/shader dump and original HUD environment were not preserved.

**Attribution:** the 11A generic pipeline error is **consistent with** the optional DXVK HUD text shader failing on the old macOS DrawIndex translator. It is **not proven** because the original `DXVK_HUD` value and the actual pipeline shader module were not preserved. The standard presentation vertex shader does not itself request DrawIndex, and the exact module passed a minimal old-runtime pipeline test. For the next baseline, record `DXVK_HUD` explicitly and run both HUD-disabled and `DXVK_HUD=fps` cases; preserve the exact shader-module identity or log the DXVK built-in shader name at pipeline creation. No DXVK shader workaround is justified by this evidence.

## Isolated MoltenVK runtime-upgrade safety design

The tested bundle has a runtime-local ICD manifest at `runtime/wine/lib/moltenvk-vkmt/MoltenVK_icd.json`; it resolves `./libMoltenVK.dylib`. The bundle also contains MoltenVK names under `lib/wine/x86_64-unix`. The actual loaded paths must be resolved by the separate runtime-identity audit before selecting replacement destinations; a matching basename is not enough.

1. Keep the 11A extraction immutable as the negative control. Make a byte-verified disposable copy at a new candidate path; do not use hard links. Hash the old candidate's loader, `winevulkan.so`, ICD manifest, and all MoltenVK paths before and after every run.
2. Build from the exact pinned upstream 1.4.2 source/tag and its recorded dependency revisions. Verify that the produced dylib contains an x86_64 slice with `lipo`, and record its SHA-256, deployment target, `LC_ID_DYLIB`, `LC_LOAD_DYLIB`, `LC_RPATH`, and compatibility/current versions. Keep the `@rpath/libMoltenVK.dylib` install name and manifest-relative layout expected by the runtime; use the candidate's own ICD manifest and candidate-local library search paths.
3. Replace only the MoltenVK dylib payload (and its candidate-local ICD manifest if its identity/path metadata differs) at the path proven to be loaded. Do not rebuild or replace Wine, `winevulkan.so`, DXVK DLLs, or `libvulkan.dylib` unless the identity audit demonstrates a specific loader-link reason. Do not point the candidate at Homebrew's loader/ICD or edit Homebrew, system paths, Highball, or any game prefix.
4. Verify the native direct probe and the x86_64 Wine process independently. Capture `DYLD_PRINT_LIBRARIES` plus `dladdr`/loaded-image identity for the Vulkan entry points and driver, and use a candidate-specific `VK_ICD_FILENAMES`. Require the expected candidate dylib path, x86_64 slice, Apple M3, portability enumeration/subset, and successful device creation. `winevulkan` and DXVK consume the standard Vulkan loader/ICD ABI; no Wine or DXVK change is inherently required for a driver-only update, subject to the `otool` identity and loader-path checks above.
5. Run an A/B matrix against the same exact SPIR-V inputs: `dxvk_present_vert` as a control and the generated HUD vertex module (or a minimal explicit DrawIndex shader) as the capability case. The old control should compile and DrawIndex case should fail; the candidate should compile both. Then run the same pinned DXVK DLL hashes under the same Wine 11.17 runtime copy, changing only the proven MoltenVK payload. Record the exact HUD environment. This distinguishes the DrawIndex fix from unrelated rendering or loader changes.

This is an isolated-test design, not a verified ABI claim for a candidate binary: no 1.4.2 runtime was built or staged in this subtask. Exact upstream tag/commit, SPIRV-Cross revision, binary compatibility metadata, and final loaded path remain for the version and runtime identity audits to pin down.

## New-runtime black output: read-only source findings

The parent task reports that native Vulkan clear output on the 1.4.2 candidate is visibly red/green, while the same candidate under Wine/DXVK presents a black window. The 30-second Wine test still records successful D3D11 `Present` calls, visible/foreground window state, and process exit status 0. Its enhanced frame-statistics log records advancing DXGI present counts. The new MoltenVK debug log translates and compiles the ordinary DXVK presentation vertex/fragment shaders and the optional HUD DrawIndex shader; there is no SPIR-V-to-MSL error in that run. The parent reports no Metal API validation errors. The D3D11 clear-color test source requests four visibly distinct colors and clears the render target every iteration.

These observations establish that the old DrawIndex translation failure is repaired in the candidate and that Wine/DXVK reaches a clean, successful-present path. They do **not** prove the application backbuffer contains those colors, that the presentation blit samples them correctly, or that the Wine `WineMetalLayer` content is composited visibly. The MoltenVK debug shader dump proves translation/compilation, not GPU output pixels. Source tracing confirms the path is `ClearRenderTargetView` → app backbuffer → `DxvkSwapchainBlitter::present` → acquired WSI image → `vkQueuePresentKHR`; no one stage is identified by current logs as the black-output cause.

**Black-output status:** root cause **NOT PROVEN**. Plausible fault boundaries remain (a) D3D11 clear/source backbuffer contents, (b) descriptor or sampling/composition in the DXVK blit, or (c) Wine's layer/display composition. Native Vulkan clear success narrows the issue to the Wine/DXVK path, but does not distinguish those boundaries. Do not label Gate 1 healthy based only on HRESULTs, successful pipeline compilation, clean exit, or absence of API-validation messages.

The smallest next diagnostic should capture source and destination contents at the three boundaries without changing renderer behavior: check a known clear color in the D3D11 source image, check the acquired Vulkan WSI image after the blit, then compare the submitted WSI image identity/presentation with the Wine layer. A source-side and WSI-side readback or a supported GPU frame capture can isolate the first divergence; first verify that the capture itself does not change scheduling. Until that evidence identifies a fix and a visible 60-second run passes, Gate 1 remains failed and Gate 2 must remain stopped.

## Evidence classification

- **VERIFIED from pinned source/build and new-runtime log:** ordinary WSI blit vertex shader source, generator rule, captured SPIR-V `VertexIndex` decoration, Vulkan 1.3 validation success, HUD source use of `gl_DrawID`, HUD indirect-draw purpose, the generic nature of DXVK's pipeline error, and successful 1.4.2 translation/Metal compilation of the DXVK HUD DrawIndex shader.
- **SUPPORTED INFERENCE:** 11A's DrawIndex error came from the HUD text shader if the original run enabled a DXVK HUD; the upstream 1.4.2 change addresses this specific translation requirement.
- **NOT TESTED here:** actual 11A shader-module identity, original `DXVK_HUD` process environment, root cause of new-runtime black output, or source/WSI pixel contents. Runtime ABI compatibility is not certified by this read-only audit; the parent task did build/run a 1.4.2 candidate, but that candidate has not passed the visible-rendering baseline gate.
