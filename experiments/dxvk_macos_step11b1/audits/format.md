# DXVK and MoltenVK RGBA8/BGRA8 format-chain audit

Scope: read-only source trace for DXGI `R8G8B8A8` and `B8G8R8A8` formats through DXVK texture creation, image views, sampled presentation blit, Vulkan WSI selection, and MoltenVK Metal formats. DXVK source is pinned at `8d348236e14a3db25ffbe528a83010b3dd69a3ef` (`/tmp/fgmetal-dxvk-macos-audit-20261004`); MoltenVK is pinned at `db66022459ffb663aa2b50f6b018bc2e124f5edf` (`v1.4.2`, `/tmp/fgmetal-step11b/MoltenVK`). Both checkouts were clean when inspected. No renderer files were edited, and this audit did not perform screen capture or pixel readback.

## DXVK texture format and view chain

`DXGIVkFormatTable` maps DXGI `R8G8B8A8_UNORM` to `VK_FORMAT_R8G8B8A8_UNORM`, its sRGB variant to `VK_FORMAT_R8G8B8A8_SRGB`, and the corresponding BGRA formats to the matching Vulkan BGRA formats. The typeless RGBA mapping starts as UNORM and its view family lists the compatible UNORM, SNORM, sRGB, UINT, and SINT Vk formats; typed RGBA UNORM and sRGB and typed BGRA UNORM and sRGB each list their linear/sRGB pair. The mapping records use the default identity component swizzle for these formats. Evidence: DXVK `src/dxgi/dxgi_format.cpp:134-147,422-444,615-626,768-781`; the identity default is in `src/dxgi/dxgi_format.h:20-39`.

The device-specific format table constructor only remaps D24 depth formats and A8 when their required support checks fail; it has no RGBA8/BGRA8 remap. `D3D11CommonTexture` takes `formatInfo.Format` as `imageInfo.format`, and when the compatible family contains multiple formats it marks the image mutable and supplies the family as its view-format list. `D3D11SwapChain::CreateBackBuffers` preserves the DXGI descriptor format when it constructs the D3D back buffer. Evidence: `src/dxgi/dxgi_format.cpp:860-883,965-989`; `src/d3d11/d3d11_texture.cpp:22-47,80-93`; `src/d3d11/d3d11_swapchain.cpp:620-655`.

For texture SRVs and RTVs, DXVK looks up the requested DXGI view format and places the resulting Vulkan format, aspect, and component swizzle in the image-view key. The Vulkan image-view creation path forwards that component mapping as `VkImageViewCreateInfo.components`. RGBA8 and BGRA8 use identity mappings. DXVK has explicit non-identity entries for other formats, including BGRX with alpha forced to one; those do not apply to BGRA8. Evidence: `src/d3d11/d3d11_view_srv.cpp:74-89`; `src/d3d11/d3d11_view_rtv.cpp:18-32`; `src/dxvk/dxvk_memory.cpp:207-219`; BGRX mapping in `src/dxgi/dxgi_format.cpp:427-433`.

## MoltenVK image, Metal format, and swizzle handling

MoltenVK maps `VK_FORMAT_R8G8B8A8_UNORM`/`_SRGB` to `MTLPixelFormatRGBA8Unorm`/`RGBA8Unorm_sRGB` and `VK_FORMAT_B8G8R8A8_UNORM`/`_SRGB` to `BGRA8Unorm`/`BGRA8Unorm_sRGB`. The BGRA UNORM descriptor uses Metal's BGRA normalized vertex format; BGRA SNORM/UINT/SINT are the cases in this group implemented via an RGBA Metal format plus an explicit format swizzle. BGRA UNORM and sRGB are not in that forced-swizzle case. On image creation, MoltenVK stores the Vk format and selects the mapped Metal pixel format for the Metal texture descriptor. Evidence: MoltenVK `MoltenVK/MoltenVK/GPUObjects/MVKPixelFormats.mm:800-814,1131-1138`; `MoltenVK/MoltenVK/GPUObjects/MVKImage.mm:1224-1239,1264-1277,165-179,2082-2129`.

For a non-identity component mapping on an image view, MoltenVK either uses a native Metal texture-view swizzle when the device feature is enabled or carries the mapping as shader metadata when it is not. The MSL pipeline options enable sample swizzling for the latter case. The feature is initialized false, then enabled for Metal Mac GPU family 2 and Apple GPU family 1. The identity mapping used by the direct RGBA8/BGRA8 mappings requires neither route to reorder channels. Evidence: `MVKImage.mm:2053-2058,2184-2187,2004-2016`; `MVKDevice.mm:2473-2475,2502-2510,2519-2530`; `MVKDescriptorSet.mm:357-371,1204-1222`; `MVKPipeline.mm:2054-2060,2496-2505`.

## Sampled presentation blit and specialization

The D3D11 present path supplies a view of the D3D back buffer and a view of the acquired Vulkan swapchain image to `DxvkSwapchainBlitter::present`. The blitter binds the source image view as a sampled image. Its shader fetches source texels and performs interpolation in the selected color space; there is no RGBA-versus-BGRA special case in that shader. DXVK builds pipeline specialization constants from source and destination color spaces, source sRGB status, destination format sRGB status, gamma state, and composition flags. If source and destination color spaces match, the source is single-sampled, and HUD/cursor composition is absent, it specializes the shader to pass through instead of converting. Evidence: `src/d3d11/d3d11_swapchain.cpp:480-529`; `src/dxvk/dxvk_swapchain_blitter.cpp:246-305,307-355,717-770`; `src/dxvk/shaders/dxvk_present_frag_blit.frag:10-36`; `src/dxvk/shaders/dxvk_present_common.glsl:6-14,67-89,92-144`.

## WSI surface format and color-space compatibility

DXVK's D3D11 swapchain preferred-format conversion requests RGBA8 UNORM for either DXGI RGBA8 or BGRA8 UNORM, and RGBA8 sRGB for either DXGI sRGB variant, while the actual D3D back buffer remains created from the original DXGI descriptor format. This preferred format is only a request: `Presenter` queries the WSI surface formats and runs its format compatibility selection. Its sRGB nonlinear compatibility list includes both RGBA8 and BGRA8. MoltenVK builds its 8-bit surface-format candidates from supported Metal `BGRA8Unorm` and `BGRA8Unorm_sRGB`; it does not add RGBA8 UNORM as an 8-bit surface candidate. Thus when only the listed BGRA candidates are available, DXVK's compatibility chooser can select BGRA8 for the RGBA8 preference. The final blit connects the D3D back-buffer view to that selected surface image. Evidence: `src/d3d11/d3d11_swapchain.cpp:742-760,620-655`; `src/dxvk/dxvk_presenter.cpp:680-694,1112-1120,1158-1172,1195-1248`; `MoltenVK/MoltenVK/GPUObjects/MVKDevice.mm:2052-2063,2092-2113`.

DXVK converts an sRGB surface format to its UNORM partner for swapchain selection, then—when `VK_KHR_swapchain_mutable_format` is enabled and the format pair exists—requests both views and imports the image internally with the sRGB view format. Without that feature/pair branch, it imports with the selected surface format. The shader separately specializes destination sRGB state based on the imported view format. MoltenVK assigns the selected Vk format to `CAMetalLayer.pixelFormat` and maps `VK_COLOR_SPACE_SRGB_NONLINEAR_KHR` to the sRGB Core Graphics color space. Its pixel-format table gives BGRA8 UNORM the `All` capability set and BGRA8 sRGB the `RFCMRB` set on macOS; `RFCMRB` includes read, filter, color attachment, multisample, blend, and resolve, while lacking the separate write/storage capability. Surface formats are emitted only for Metal formats marked supported. Evidence: DXVK `src/dxvk/dxvk_presenter.cpp:684-694,825-847,892-918,1195-1208`; MoltenVK `MVKPixelFormats.h:42-62`; `MVKPixelFormats.mm:1077-1085,1131-1138,1376-1403,1555-1594`; `MVKDevice.mm:2052-2063,2092-2113`; `MVKSwapchain.mm:501-524`.

DXVK's declared color-space fallback pair is only extended-linear sRGB ↔ HDR10 ST2084. It otherwise picks the requested color space if present, or a supported fallback (preferring sRGB nonlinear when available). MoltenVK's surface-format query forms combinations from its supported Metal surface formats and its listed color-space values, and swapchain creation maps those values to the corresponding CAMetalLayer color-space property. This is source-reported API support, not evidence about a particular display's physical HDR behavior. Evidence: `src/dxvk/dxvk_presenter.cpp:12-16,356-379,1124-1149`; `MVKDevice.mm:2074-2113`; `MVKSwapchain.mm:520-570`.

## Source-only conclusion

The inspected direct RGBA8/BGRA8 texture path preserves their distinct Vulkan and Metal format mappings and uses identity component mappings. Presentation has an explicit compatibility path from DXVK's RGBA8 preference to MoltenVK's BGRA8 surface candidates, plus separate sRGB/color-space conversion. These source paths alone do not identify why a rendered frame would be black; that requires runtime evidence at the source image, sampled blit, and acquired/presented surface boundaries. No fix is proposed by this audit.
