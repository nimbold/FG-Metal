# Step 11B1 audit — D3D11 app clear and backbuffer storage

**Pinned source:** `/tmp/fgmetal-dxvk-macos-audit-20261004`, `HEAD=8d348236e14a3db25ffbe528a83010b3dd69a3ef`.

**Scope:** Read-only trace from `ClearRenderTargetView` through the RTV/backbuffer and `GetBackBufferView` sampled by Present; inspect DISCARD allocation policy, storage rotation, image layout, and deferred-clear ordering. No renderer source was edited, and this audit used no screenshot or pixel readback.

## Source path

`D3D11RenderTargetView` creates its `DxvkImageView` from the texture's `DxvkImage` (`src/d3d11/d3d11_view_rtv.cpp:18-31,124-127`). `ClearRenderTargetView` captures that view in a command-stream lambda and calls `DxvkContext::clearRenderTarget` (`src/d3d11/d3d11_context.cpp:442-464`). For an ordinary image RTV, that call stores a deferred clear against the view; the clear is deliberately not emitted immediately (`src/dxvk/dxvk_context.cpp:362-425,2232-2257`). If the cleared view is not among the current framebuffer attachments, the path ends the current pass before deferring (`:380-395`); `endCurrentPass` only ends the render and compute passes (`:6265-6268`).

`GetBackBufferView` selects `m_backBuffers[0]`'s image and creates a color sampled view (`src/d3d11/d3d11_swapchain.cpp:391-408`). `PresentImage` first queues `EndFrame` and `ExecuteFlush`, acquires the WSI image, then captures that backbuffer view as `cSwapImage` for the present callback (`:411-440,494-508`). The callback calls `cBlitter->present` with that sampled source and acquired WSI target, then synchronizes WSI, flushes, and presents (`:517-530`). The blitter binds `srcView->getDescriptor()` as a sampled image, issues its draw through `DxvkCommandList`, and tracks the source image (`src/dxvk/dxvk_swapchain_blitter.cpp:307-357,362-364`). This direct command-list path does not call the `DxvkContext` clear-flush helpers.

## Deferred clear at Present

The application clear is asynchronous: `ExecuteFlush` appends a flush command after already-recorded D3D11 commands and dispatches the chunk (`src/d3d11/d3d11_context_imm.cpp:1092-1134`). `EndFrame` queues `ctx->endFrame()` (`:869-885`), which ends the render pass (`src/dxvk/dxvk_context.cpp:127-135`). When the flush ends command recording, `endCurrentCommands` calls `prepareSharedImages` (`:109-123,9385-9398`). That helper flushes deferred clears only for shared images already in `m_nonDefaultLayoutImages` (`:9705-9719`); the list is populated when a transition leaves an image's default layout (`:9788-9791`). Initial backbuffer setup initializes its contents and records the image back in its default layout (`src/d3d11/d3d11_swapchain.cpp:660-674`; `src/dxvk/dxvk_context.cpp:1028-1049,1142-1144`). `ClearRenderTargetView`'s defer path itself does not transition or register the image.

Accordingly, source permits a concrete unmaterialized-clear case: an app clears an RTV while that image has not been transitioned out of its default layout, then presents without a later DXVK render pass or other resource operation that flushes the clear. In that case `prepareSharedImages` has no tracked nondefault backbuffer to visit, and the direct blitter samples the image without calling those clear-flush helpers. This is a source-level hypothesis about the clear-to-Present path, not a measured pixel result. A later `prepareShaderReadableImages` call does flush pending clears (`:9684-9701`), so earlier rendering/resource use can change this path.

## DISCARD versus storage rotation

`CreateBackBuffers` sets `backBufferCount` to `m_desc.BufferCount` only for sequential effects; all other effects get one D3D backbuffer (`src/d3d11/d3d11_swapchain.cpp:616-620`). It sets `DXGI_USAGE_DISCARD_ON_PRESENT` for `DXGI_SWAP_EFFECT_DISCARD` and `DXGI_SWAP_EFFECT_FLIP_DISCARD` (`:647-658`). In the pinned `src` tree this flag has no other non-header use. Present calls `RotateBackBuffers` only when `m_backBuffers.size() > 1` (`:532-535`). Thus DISCARD and FLIP_DISCARD use one backbuffer here and do not rotate or replace its allocation on Present. The DISCARD flag alone does not trigger storage invalidation in this code.

For multi-buffer sequential effects, Present queues the blit/present callback first, then queues `RotateBackBuffers`, then flushes the chunk (`:494-535`). Rotation cycles the allocations among the existing `DxvkImage` objects (`:554-572`). Invalidation flushes a pending deferred clear only when that image is found in the current framebuffer's attachment list; the flush occurs before storage assignment (`src/dxvk/dxvk_context.cpp:1417-1429,1451-1459`). An unbound RTV clear can fail that `found` condition. If such a clear remains deferred across sequential rotation, it remains associated with the same image/view object while the image receives different backing storage. Storage assignment updates the image's backing info and increments its version; image views refresh their cached descriptors on the next `getDescriptor` (`src/dxvk/dxvk_image.cpp:353-406`; `src/dxvk/dxvk_image.h:956-965`). Therefore this code permits a pending clear to be materialized against the post-rotation allocation in that conditional path. It does not describe the single-buffer DISCARD path.

## Source-only conclusion

The pinned implementation has no DISCARD-triggered backing-store rotation for the tested one-buffer effect. It does defer D3D11 RTV clears, and Present's direct sampled blit does not itself use the context clear-flush path. An unbound/default-layout clear can therefore remain pending through the blit; on multi-buffer sequential effects, it can also survive the conditional invalidation guard and follow the image object to new storage. Whether this explains the reported black output remains unverified by this source audit; WSI clear and blitter probes are needed to distinguish the runtime boundary. No fix is proposed here.
