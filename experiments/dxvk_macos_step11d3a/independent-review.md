# Independent static review — native MoltenVK instrumentation

Reviewed `moltenvk-instrumentation.patch` SHA-256 `a9795dae571d4ea50cede0c50973b6f2298c1e7caeb19be638697114936d1cef` and `REPORT.md`. `git apply --check --stat` succeeds against the pinned pristine source; this review did not apply the patch, build, test, or run the experiment.

## Findings

- **Timing validity is limited by synchronous instrumentation.** The opt-in writer takes one process-wide mutex and performs many synchronous `fprintf`/`fputs` calls, flushing every 64 events (patch lines 139–170). It runs inside `_availabilityLock` for `acquire_image_assigned` and `make_available` (202–209, 393–400), so trace I/O can delay state transitions while holding MoltenVK's image lock. The acquire API interval also encloses the nested `acquire_image_assigned` write (493–516 and 202–209). The explicit `call_begin_ns`/`call_end_ns` correctly bracket `nextDrawable` and the timed Vulkan implementation calls, but they do not make the instrumentation behavior-free; the acquire interval includes that nested logging, and surrounding synchronous writes perturb scheduling and throughput. Treat resulting tails/cadence as instrumented observations unless overhead is separately bounded. Static inspection found no direct lock-order cycle or logger callback into MoltenVK; this is not runtime deadlock validation.
- **Use call bounds, not event timestamps, for durations.** For example, `next_drawable_begin` is emitted before `traceStartTime` is sampled (225–228); queue/acquire begin events likewise precede `traceStartNs` (446–452, 493–502). Thus each begin event's `timestamp_ns` is an earlier log timestamp, not the call boundary. The end record's explicit `call_begin_ns`, `call_end_ns`, and `duration_ns` are the relevant values. Since timestamps are sampled before taking the global writer lock while event IDs are assigned after taking it (142–149), serialized `event_id` order is not guaranteed to be timestamp order across threads.
- **Acquire output guard: resolved in the refreshed patch.** Both acquire wrappers now require `VK_SUCCESS` or `VK_SUBOPTIMAL_KHR` before inspecting `*pImageIndex`, then check the image-count bound (patch lines 509–513, 587–591). Static review confirms the trace-side uninitialized/unspecified output read identified in the previous review is guarded. No build or runtime validation was performed.
- **Frame-level correlation needs a cross-trace join.** `frameIndex` is present in the MoltenVK schema but no producer sets `hasFrameIndex` (patch lines 23, 160). Generic `queue_submit_begin/end` records carry only queue and duration, with no submit ID, command-buffer/image/acquisition sequence (446–460, 469–483). The native app does record its own frame IDs and API intervals, so joins may be made using same-process thread/API intervals and the acquire ordinal; no source-side frame-ID key makes this automatic. Treat pointer strings as process-local identities, not globally unique IDs, and validate any image/swapchain-handle mapping before using it. `drawable_release` and `make_available` also omit swapchain identity (366–400), weakening correlation if addresses are reused.
- **App clock-label correction remains pending verification.** In the current `native_control.mm`, `MachAbsoluteNanoseconds()` uses `mach_absolute_time()` (46–59) and the renderer labels run timing as Mach absolute (435–439), while experiment metadata still says `mach_continuous_time` (1675). Verify the app agent's final source before relying on clock-domain/phase analysis; this is a metadata mismatch in the reviewed snapshot, not evidence that captured values use continuous time.
- **Trace durability/startup are not attested by the patch.** An invalid/unwritable `FG_NATIVE_MVK_TRACE` path silently leaves tracing disabled (98–103, 127–130); the file is append-opened, and no explicit final flush/close exists beyond periodic flushing (170). A runner must verify the file opened, capture/validate the expected trace and preserve complete records after process exit; missing output cannot be read as zero events. The string writer does not escape JSON, though current event/detail values in this patch are literals.

## Report and evidence boundary

`REPORT.md` accurately labels itself preparation-only, says no native build/process/smoke/baseline ran, marks all native samples/configuration unavailable, and states A1/A2 are unsupported (lines 3, 23–30, 48, 52, 64–78). Do not draw a graphics-health or starvation conclusion from this artifact. Its storage discussion describes lifecycle/admission blockers, not a Gate 0 threshold refusal. The patch itself adds trace instrumentation; it does not change the listed drawable-count, timeout, queue-submit, acquire-placement, or presentation-scheduling settings. The primary remaining evidence gaps are a valid managed build/run/POST path, verified trace capture, measured native configuration and validated cross-trace joins, plus the smoke and repeated baseline runs. App syntax validation alone is not runtime evidence.

## Primary follow-up verification

After this independent review, the primary agent verified the final native app has no continuous-time labels and uses mach_absolute_time throughout. The final app passed a read-only clang++ syntax check against the pinned Vulkan headers, with no generated executable/object. The source hands the actual CAMetalLayer to the renderer before worker startup, bounds-checks acquire image access, uses app_acquire_sequence as a distinct sequence domain, brackets API calls after begin-event writes, and references the actual 11D.2 BGRA8/three-image WSI log. This resolves the clock-label issue by primary static verification, without representing an independent runtime re-review. The remaining logging, mapping, display/configuration and lifecycle evidence limitations above remain.
