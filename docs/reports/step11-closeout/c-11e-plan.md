# Step 11E Readiness and Minimal A/B Transport Plan

## Recommendation

**11E_READY = NO for the current executable/source as-is.** The public FG-Metal submission contract accepts previous and current textures, and the Metal backend retains both through GPU completion. The retained R5 integrated provider path, however, accepts one source texture per job; its earlier standalone Vulkan proof is also a sequence of one-source jobs, not one A/B submission. The current R5 FLIP_SEQUENTIAL evidence additionally leaves two-buffer backing rotation unverified. A safe 11E run needs the narrow two-source bridge and source-binding/lifetime/reset/release-ledger evidence below before measurement.

The repository does not define a Step 11E product resolution matrix or a Step 11E latency/throughput acceptance threshold. **640×360 at 30 Hz** is the most concrete prior integrated diagnostic workload, not an established product target. Resolve and record the intended real resolution(s) before calling a run full-resolution or using it to close product performance.

- `experiments/dxvk_macos_step11dR/evidence/STEP11D1_REPORT.md:3-5, 127, 134-149` records the R5 result as partial; it explicitly says the exact-R5 FLIP_SEQUENTIAL app accounting passed while the two-slot rotation invariant remained unverified (`p0_2_pass=false`). ## Pair identity, ownership, and synchronization to prove

1. **Bind app frame to source allocation.** For each D3D11 AppFrameId, record swapchain generation, the actual FLIP_SEQUENTIAL back-buffer index/allocation identity, dimensions/format, and source-copy/history resource identity. Establish by trace that the copy reads the application-rendered source before rotation. Do not infer source identity from a modulo counter or a returned `GetBuffer` pointer alone. The previous zero-backbuffer-event FLIP trace (`STEP11D1_REPORT.md:127`) does not prove this mapping.
2. **Form only a valid consecutive pair.** Label each copied source by AppFrameId/sequence, clock domain/epoch, and generation. First source after startup/reset seeds A; a later valid source B pairs only with the intended predecessor in the same generation/epoch. A skipped source, resize/recreate, format/device change, or clock reset invalidates the candidate pair and requires reseeding. `FrameTiming` permits sequence gaps generally (`include/framegen/backend.hpp:83-98`); the first transport proof should explicitly log consecutive IDs so the pair relation is unambiguous.
3. **Keep A and B alive through Metal use.** The bridge packet and native job need two distinct source handles (or equivalent explicit A/B identities); both must remain retained until Metal GPU completion. Retain the distinct OUTPUT until its Vulkan consumer has finished. A small source-ring is safe only with per-source job references; with a two-job maximum and adjacent overlapping pairs `(0,1)` and `(1,2)`, three history allocations suffice only if the shared source-1 reference is counted and not overwritten early. A simpler first run can serialize one pair at a time. Never increase the R5 slot count implicitly.
4. **Use GPU ordering, not CPU blocking.** Vulkan completes writes/copies for both inputs before signaling READY. Metal waits on READY, reads A and B, writes a distinct output texture, and signals DONE. Vulkan waits on the committed/successful DONE value before consuming OUTPUT through the existing internal consumer/presenter path; it then signals/records CONSUMED. Preserve monotonic values and pair every event with job ID, generation, and source IDs. Do not enqueue a Vulkan wait for DONE if Metal did not commit or if failure means DONE cannot signal. These follow the existing contract and observed R5 ordering (`STEP11D1_REPORT.md:45`; historical integration report `REPORT.md:79-86`).
5. **Reset and retire by generation.** On reset/recreation, mark old pairs ineligible immediately, reject stale-generation consumes, and keep old resources until already-submitted GPU references reach a terminal safe point. Log the reset/seed frame and each pending job’s outcome. The reset must not turn an old A plus new-generation B into a valid pair.
6. **Close a bounded release ledger.** For every opportunity record exactly one accepted pair or explicit drop reason; for each accepted job record one terminal result and one release for every source/output slot/reference. Track READY/DONE/CONSUMED, producer/consumer completion, generation invalidation, and drain. Assert the configured maximum in-flight count, no premature source overwrite, no duplicate or missing release, and zero owned resources after normal drain. R5 D1 has observed captured-job terminal uniqueness, but five of six cadence logs missed a final `job-retired` marker; shutdown closure and several failure/reset paths remained unproven (`STEP11D1_REPORT.md:45-49, 74-110`).

## Shortest useful experiment sequence

1. **Resolve the target matrix first.** Record the owner-approved real source resolution(s), format, source cadence, display/present mode, app and runtime hashes, GPU/device, and exact FLIP buffer count/mode. If no product resolution is designated, call 640×360 a diagnostic only and leave full-resolution readiness unresolved. A diagnostic-size transport probe may help debug the bridge, but it is partial evidence only: it cannot count as a valid/completed 11E run or change `11E_READY` until the target-resolution scope is explicitly resolved.
2. **Source-binding preflight.** Run the controlled D3D11 source application with changing GPU-rendered frames at the selected resolution and exact two-buffer FLIP mode. Capture a trace showing AppFrameId→back-buffer allocation/index→Vulkan history allocation before/after rotation for several consecutive frames, including one recreation. Stop if the actual allocation mapping is unavailable or ambiguous.
3. **One real A/B job.** Build a two-input diagnostic transport kernel whose output depends on both inputs (a simple fixed blend is sufficient; this is a transport sentinel, not an interpolation-quality test). Submit two consecutive app-rendered source frames as A/B through the integrated bridge; verify two distinct source identities in the Metal bind/commit record, a distinct output, READY→Metal completion→Vulkan consumer ordering, and one closed release ledger. Do not use the 64×64 standalone proof as a substitute.
4. **Bounded cadence sample.** After the single-pair proof, stream the same controlled source at the recorded baseline cadence. Begin with a bounded two-job maximum and the selected R5-compatible resource policy; log every pair, drop, reset, terminal, consumer, and release. Include one forced resize/recreation while work is pending and prove old pairs are rejected and drained before new-generation pairing. Keep the sample window and repeat count explicit; do not claim performance acceptance until a project threshold exists.
5. **Drain and reconcile.** Stop source production, drain GPU work without an arbitrary delay, reconcile every job/resource/consumer against the ledger, and require zero outstanding ownership. Preserve manifests/logs and report missing timing or event data as unavailable rather than inferring it.

## Measurements and decision boundaries

Report raw sample counts plus p50/p95/p99/max for the following where the relevant clock is valid:

- Source presents/frames per second, valid consecutive pairs per second, pair/drop counts by reason, Metal jobs/commits/completions, Vulkan output-consumer submissions/completions, and internal WSI successes/retirements.
- CPU durations for source capture/copy submission, bridge entry/return on each side, native job creation/encoding/commit, status polling, Vulkan consumer submission, and process CPU time. Keep tracing bounded and avoid synchronous per-frame disk writes.
- GPU execution duration from reliable Metal GPUStartTime/GPUEndTime; READY wait/availability to provider entry/commit; commit-to-callback; DONE-to-Vulkan-consumer completion; and total B-arrival-to-output-consumption only if timestamps are mapped to a common monotonic clock with measured error bounds. Otherwise report per-clock durations separately.
- Peak active jobs and source/output references, per-stage queue depth, and all ledger closure counters.

**Existing threshold:** the historical D1 frozen single-source R5 cadence gate required an unmonitored median of at least 55 WSI/s and failed if two of three unmonitored runs fell below 52 WSI/s (`STEP11D1_REPORT.md:24-28`). Do not transfer that R5 gate to the new two-source workload. **No 11E GPU-time, end-to-end latency, cadence, soak-duration, or full-resolution PASS threshold is defined** in the roadmap; publish measurements without inventing a PASS line. Structural pair identity, safe lifetime/synchronization/reset behavior, bounded ownership, and complete drain are prerequisites for a useful result, not substitute performance thresholds.

## Execution prerequisites and limitations

- Current R5 evidence establishes one-source transform/consumer behavior. The retained provider source and the current public API are not by themselves an integrated A/B implementation; a source-bound two-texture packet, native A/B binding/retention, and renderer AppFrame binding/reset ledger are required before the 11E runtime experiment.
- Historical R5 exact-run claims bind to frozen DLL/provider/runtime hashes (`STEP11D1_REPORT.md:7-13`); the detailed bridge implementation above is in the old sibling checkout. It must not be treated as rebuildable current-main source. Any later run needs a newly recorded exact source/build/runtime identity and the applicable storage/admission evidence. This audit did not launch or modify a runtime.
- The active checkout is macOS on Apple M3. The earlier R5 measured integration used Wine 11.17/WineForge 0.6.0.5 and MoltenVK 1.4.2 (historical `bridge-gpu-proof/REPORT.md:13`); `wine` was not found on the current shell PATH during the environment check. Availability of a separately staged Wine/runtime is not established here.
- Neither `ROADMAP.md` nor `TASKS.md` identifies a real product target resolution. 128×72 is a synthetic benchmark size (`TASKS.md:48`); 64×64 is the standalone bridge proof; 640×360 is the previous controlled integrated diagnostic; RIFE scratch calculations at 1920×1080/3840×2160 (`docs/provenance/rife-v4.26.md:87`) are not transport targets. Resolution remains an explicit prerequisite. A diagnostic-size run cannot satisfy or close Step 11E.
