## What the current source tree provides

The renderer-neutral core already accepts an ordered previous/current pair: `include/framegen/frame_generator.hpp` exposes `FrameGenerator::submit`, and `src/core/frame_generator.cpp` validates increasing source sequence/timestamps, matching texture description, and same backend/device. `include/framegen/texture.hpp` documents reference-owned opaque GPU resources and no CPU pixel access. The Metal backend and placeholder path live under `src/metal/`.

These are useful API-level hooks, not proof of the R5 DXVK/Wine path. The core source tree does not contain the R5 Vulkan adapter/provider integration or a Step 11E run harness/spec. The accepted D1 report and preserved manifests identify the earlier bridge/provider binaries, but `source-latency-lifetime-audit.md` says the provider implementation and per-object retain/release ledger were not present in that source snapshot. Therefore an 11E run must bind the exact loaded DXVK, bridge, and provider identities and produce its own ownership evidence; generic `Texture` semantics or the C.1R2 WSI shutdown result cannot substitute for that evidence.

## 11D.3-C decision

The project materials establish that 11D.3-C is gated, but do not define what C entails or state that 11E depends on it. The only supported connection is to the Native/Wine/BR9R diagnostic branch: the BR9R reports discuss gated Native comparisons and repeatedly say not to start 11D.3-C automatically. H6 now closes that branch for active engineering work while retaining the scientific classification N3. On the project’s own decision rule—unfinished work must protect an invariant used by 11E—11D.3-C is **DEFERRED**, not architecturally required before 11E.

## 11E plan boundary and shortest path

No project-owned Step 11E plan/spec or clear product-real resolution target exists. `ROADMAP.md` line 3 explicitly omits dates and performance targets until a measured baseline; `TASKS.md` does not define 11E resolutions. Existing 640×360 DXVK/Wine test runs are diagnostic harness dimensions, not a declared product target. The 11E plan must report that resolution ambiguity and bind any measured dimensions to the actual source/runtime; it must not silently promote 640×360 into a product target or invent performance thresholds.

**Shortest recommended path:** keep H6 as the terminal BR9R/R5/T8 record; do not run 11D.3-C or H7/H8. Write the 11E plan from the supplied objective, state the unresolved product-resolution target, bind the exact R5/provider/runtime, and run one bounded two-source GPU-only Vulkan→Metal→Vulkan experiment that includes pair rotation, reset/stale-history rejection, final-job retirement, and real-resolution timing. Then perform the requested correctness, performance, and adversarial reviews and stop at the explicit backend/provider strategy review.
