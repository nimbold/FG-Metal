## DXMT presentation ownership and call flow

DXMT creates a distinct swapchain object and `Presenter` for each target. The current source paths are linked at the exact audited commit:

1. D3D11 swapchain construction creates a Wine Metal view/layer and its `Presenter` ([`d3d11_swapchain.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/d3d11/d3d11_swapchain.cpp#L120-L148)). D3D12 creates the same pair in its swapchain path ([`d3d12_swapchain.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/d3d12/d3d12_swapchain.cpp#L160-L184)). Wine/macdrv owns the native window/view lifecycle; DXMT owns its renderer `Presenter` and uses the associated `CAMetalLayer`.
2. D3D11 `Present1` resolves the current DXMT backbuffer, `SyncInterval`, and presenter state, then enqueues `ctx.present(...)` ([`d3d11_swapchain.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/d3d11/d3d11_swapchain.cpp#L738-L817)). D3D12 selects a backbuffer and submits through its command queue ([`d3d12_swapchain.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/d3d12/d3d12_swapchain.cpp#L705-L719), [`d3d12_command_queue.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/d3d12/d3d12_command_queue.cpp#L390-L417)).
3. DXMT's resource tracker captures the source texture and the `EncoderType::Present` branch runs after the app's render commands, just before the presenter encodes the final copy/render ([`dxmt_context.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/dxmt/dxmt_context.cpp#L532-L546), [`dxmt_context.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/dxmt/dxmt_context.cpp#L1087-L1105)). This is the narrowest source-capture and generation-submission hook.
4. `Presenter::encodeCommands` acquires `layer_.nextDrawable()`, draws/scales the source texture into that drawable, applies DXMT's gamma and HDR/color transforms, and returns the drawable ([`dxmt_presenter.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/dxmt/dxmt_presenter.cpp#L154-L185)). DXMT then schedules `presentDrawable` or `presentDrawableAfterMinimumDuration` ([`dxmt_context.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/dxmt/dxmt_context.cpp#L1090-L1105)). The command buffer is committed by DXMT's command queue ([`dxmt_command_queue.cpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/dxmt/dxmt_command_queue.cpp#L155-L162)).
5. `WMT::Texture` and drawable handles cross the Wine Metal thunk boundary; the native side ultimately holds actual `id<MTLTexture>`, `CAMetalLayer`, and `CAMetalDrawable` objects. See [`Metal.hpp`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/winemetal/Metal.hpp#L223-L273), [`winemetal_unix.c`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/winemetal/unix/winemetal_unix.c#L1303-L1315), and [`winemetal_unix.c`](https://github.com/3Shain/dxmt/blob/fb4515681daefb789a4d0f403c4bdbca88f3b3de/src/winemetal/unix/winemetal_unix.c#L1595-L1607).

Generated output should re-enter DXMT's same `Presenter` conversion path so output format, gamma, scaling, and color handling stay coherent. It must not use a second `Present` on the game's DXGI swapchain. Do not retain a drawable while Framegen runs; acquire one only for the scheduled display opportunity.

## Adapter, synchronization, and scheduler assessment

The existing Framegen `metal::Device` can `wrap_texture`, associate source metadata, `make_event_dependency`, and export a generated texture plus completion event through `event_point`/`native_texture`. The import is zero-copy and retains the `MTLTexture`; it does not snapshot pixels. A native Objective-C++ adapter should bridge WMT handles to native Metal objects on the Unix side, while DXMT's cross-built renderer code continues to use WMT handles. The renderer-neutral `FrameGenerator` and `PresentationScheduler` can remain outside DXMT's renderer types. The C++ API can share one Metal backend per `MTLDevice` and create one `FrameGenerator` stream per presenter. In contrast, each current C ABI context creates its own Metal backend/queue/model and allows one active stream; using C contexts for multiple targets would duplicate those resources unless the provider/API is changed. Keep independent history, scheduler, and lifecycle epoch per swapchain instance.

For synthetic-first testing, the generic `FrameGenerationBackend` SPI with `FrameGenerator::create` and custom `TextureResource`, `GpuSyncPoint`, and `GpuCompletion` wrappers avoids the RIFE-only `metal::Device::create` initialization path. A standalone test-only Metal blend provider using that SPI now exists under [`experiments/dxmt_framegen/synthetic/`](../../experiments/dxmt_framegen/synthetic/); it did not change the public core API. This closes the test-provider availability gap only. It does not provide the native WineMetal texture bridge, DXMT queue ownership, source-history copy, or DXMT presentation path. The production RIFE adapter can later use the Metal device wrapper and existing GPU-native completion/event contract.

The adapter still needs an explicit map between scheduler request IDs, source-history textures, Framegen submissions/tickets, and generated output. The scheduler carries frame IDs/timestamps but no texture handles. A retained DXMT `MTLTexture` object does not preserve its pixels when the D3D11 backbuffer is reused; copy/convert each accepted source into a distinct library-owned history texture before reuse. The clearest initial seam is the Present encoder before DXMT's gamma/scale/HDR presentation shader: keep source and generated history in the same pre-transform color space, then pass either through that shader once. If instead history is captured after the transform to match displayed pixels, the generated result must bypass or invert that transform; applying the Presenter shader again would double-transform it. WMT `obj_handle_t` values are thunk handles, not Objective-C pointers; the adapter must invoke the native Framegen Metal API on or through the native Wine Metal side rather than cast a DXMT-side `WMT::Texture` handle directly to `id<MTLTexture>`.

Signal an `MTLSharedEvent` after the source/history copy, let Framegen wait on that dependency on its own command queue, and make DXMT wait on Framegen's completion before sampling generated output. Framegen's imported source and generated textures are retained across C API tickets; do not recycle a history slot until the Framegen client lease and both producer/consumer GPU uses have retired. Shared events order queues but do not represent producer success: if a failed source-copy command buffer never signals, an already-encoded Framegen wait can stall its serial Metal queue, and resetting history cannot cancel that wait. Prefer to gate Framegen submission on successful source-copy completion via an asynchronous completion/status path, then bypass late or failed copies; otherwise prove queue recreation and ticket retirement recover safely. For a C API adapter, every issued ticket must reach exactly one terminal generated/bypassed/dropped notification. If DXMT samples G, report a consumer completion event after that command buffer; do not use the borrowed generated handle after ticket retirement. The C++ adapter must retain its `GeneratedFrame`, texture, and completion until consumer use is finished. The same-queue presenter must not enqueue a wait on a still-pending generated frame, because that can block subsequent game rendering and source presentation. Poll ticket readiness and select G only when ready before deadline, or use an isolated presentation queue whose waits cannot hold DXMT's source queue. The normal frame path must not CPU-wait for generation.

The following requirements still block the requested DXMT-native synthetic path:

- The model-free Metal test provider now uses `FrameGenerator::create` and the backend SPI, but it owns an app-local Metal device and MTKView. It has not been linked into DXMT/Wine or exercised with DXMT backbuffers. The old `placeholder-synthetic-motion` benchmark JSON remains evidence from an earlier experiment, not a runtime backend. `metal::Device::create` remains RIFE-specific and rejects initialization when weights are unavailable.
- The RIFE Metal provider requires matching opaque RGBA8 SDR textures and `wrap_texture` accepts only single-sample 2D textures. DXMT can expose BGRA/RGBA 8-bit, R10G10B10A2, RGBA16Float, and multisampled sources; the adapter must resolve multisampled inputs and GPU-convert eligible sources into owned RGBA8 textures or bypass unsupported formats. RIFE must stay disconnected until synthetic DXMT presentation is stable.

The pacing gap is equally important. DXMT currently derives a relative `vsync_duration` from the application's `SyncInterval` and a refresh-rate estimate, sets its layer's display-sync behavior off, acquires drawables on source `Present`, and schedules with `presentDrawableAfterMinimumDuration`. `nextDrawable()` may wait up to one second when the finite drawable pool is exhausted and then return nil ([Apple documentation](https://developer.apple.com/documentation/quartzcore/cametallayer/1478172-nextdrawable)); DXMT calls it inside `Presenter::encodeCommands()`, dereferences the drawable texture without a nil check, and measures the whole encode call rather than acquisition alone. There is no current `CAMetalDisplayLink` integration, display-opportunity callback, host render deadline, target presentation timestamp, or actual visible-presentation feedback in this presenter path. Framegen's existing scheduler expects those timing inputs.

For the default balanced 2x scheduler at 30→60, source frames A=0 ms and B≈33.3 ms target G at roughly 50 ms, with a generation-ready cutoff near 46.7 ms. After warm-up, the intended display opportunities are A at about 33.3 ms, G at 50 ms, and B at 66.7 ms, then G(B,C), C; this adds about one source interval of startup/display latency. These are scheduler targets to validate on hardware, not measured DXMT timings. A 40→80 or 60→120 mode was not tested because the built-in panel exposes only 60 Hz modes.

A display-driven path needs to bridge a native `CAMetalDisplayLink` callback, its callback drawable, timing fields, and presentation feedback across the Wine Metal thunk boundary, or keep the scheduler and output decision on the native side. A native-side scheduler avoids a blocking reverse callback on the display-link run loop; an asynchronous event bridge is the alternative if policy remains in DXMT. Define whether a source timestamp means accepted `Present` time or source-ready time. Normalize that timestamp, callback/deadline/target times, generated-ready time, and actual `presentedTime` into one monotonic nanosecond epoch; DXMT's current `high_resolution_clock` use measures durations and does not establish that shared epoch. The path must record actual presented/dropped outcomes and expose an isolated drawable-acquisition measurement. A display callback must not wait for game `Present`, generation completion, or a blocking drawable request. The existing source-Present path alone cannot establish correct A → G → B order or 30→60 timing.

## Lifecycle and multi-swapchain boundary

Each swapchain has its own `Presenter`; this is a sound location for independent state. DXMT has no current primary-target selector. Primary selection is a proposed policy, not an existing capability: select by stable swapchain-instance identity and explicit configuration, and abstain when visibility or target ownership is ambiguous. Leave all other targets on the original path. Do not key history by `HWND` alone; use a swapchain-instance identity plus lifecycle epoch.

On discontinuity, invalidate the current adapter epoch before retiring or replacing any old resources. Reset history, discard in-flight stale output, and bypass until two valid, ordered source frames with the new epoch and descriptor signature arrive after resize/`ResizeTarget`, drawable-size or source dimension/format/sample-count/colorspace change, gamma/HDR/EDR/display-setting-version change, display timing-generation change, device loss, fullscreen/monitor/focus/occlusion transition, swapchain destruction/recreation, or explicit enable/disable. Display timing-generation notifications are a future adapter input; current DXMT has no display-link timing event. On device loss, retire the old Framegen context and create a new one only after DXMT provides a valid device; the current C API's device-lost invalidation is not a same-context recovery. Focus, minimization, and occlusion detection is incomplete, so the adapter must abstain or bypass when target visibility is uncertain. Enter bypass before fullscreen/window/monitor transitions, then reconcile actual state even if a transition returns failure or only partially succeeds; DXMT can update internal fullscreen/monitor state before a window operation fails. `Presenter::synchronizeLayerProperties` observes display-setting version changes, which the adapter must also treat as an epoch change.

Late or failed work must release textures and preserve exactly one normal source presentation for each application Present; generated layer refreshes must not advance the DXGI-facing source count or backbuffer identity. A `nextDrawable()` timeout/nil result is another fail-open edge: acquire only after the display decision is committed, do not hold it while generation runs, and define a fallback when acquisition fails. Repeated backend, allocation, or synchronization failures require a host-side circuit breaker and explicit recovery condition; scheduler cooldown for deadline misses is not that circuit breaker. Destruction must stop new submissions, serialize teardown, and retire resources against Framegen producer and DXMT consumer GPU completion; the D3D12 swapchain destructor does not visibly wait for the DXMT queue before releasing its view.

Existing source limitations relevant to a later test matrix:

- D3D11 has partial minimized/occlusion/focus gates, but flip-model occlusion is not fully reported.
- D3D12 has weaker minimized/focus gating; its `SetHDRMetaData` returns before the metadata-handling code, so HDR metadata is currently ignored. Its resize path also has a command-queue flush TODO.
- Layer properties invalidate pipeline state on source format, color-space, and sample-count changes; dimensions update the layer. The adapter must track all source descriptor fields independently and reset on incompatible source changes.
- Framegen C API resource callbacks may run on worker threads; adapter callbacks must be thread-safe and nonblocking, with no lock-order dependency on DXMT's renderer or teardown path.

### Isolated synthetic Metal/display host

The test-only host under [`experiments/dxmt_framegen/synthetic/`](../../experiments/dxmt_framegen/synthetic/) uses Framegen's generic backend SPI, two fixed synthetic source patterns, a GPU blend kernel, Metal shared-event ordering, and `CAMetalDisplayLink`'s supplied drawable. It changes no Framegen public API or core and does not link into DXMT. It records source updates, callback/target/deadline times, generated readiness, selections, and drawable presentation feedback without pixel readback. Source and blend submission work also runs from the display callback; it does not CPU-wait for the GPU, but callback-side allocation/encoding can affect deadline measurements and is unlike a dedicated presentation owner. The x86_64 Mach-O builds, but its single launch stalled before the first architecture log; no stack evidence attributes the stall to a specific Metal call. Native arm64 callbacks therefore only test this standalone host.

The initial arm64 v1–v3 traces all ran for about 60 seconds. V1's callback polling yielded one selected G; v2's callback-time phase mismatch yielded 636; v3 selected 1,572 G, alongside 28.823 source updates/s and 58.433 callbacks/s. Those traces predate the raw-deadline fix and **do not validate deadline gating in the current source**. V3 also does not establish a correct A/G/B source sequence: its selections contain repeats and source-ID regressions (for example `G` for source 10 followed by `A` for source 9). The raw source identifiers and event times remain available in the [v3 CSV](../../experiments/dxmt_framegen/evidence/step10b/arm64-v3/synthetic-display.csv). Its reported p50/p95 actual-minus-native-target offsets are 66.167 μs/16.769 ms; 644 of 3,557 timestamped rows exceed 8.33 ms. The phase-normalized scheduler feedback is a coordinate conversion into callback time, not an independent timing validation.

The display link supplied `targetTimestamp` as the render-submit deadline ([Apple documentation](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink/update/targettimestamp)) and `targetPresentationTimestamp` as a separate estimated target ([Apple documentation](https://developer.apple.com/documentation/quartzcore/cametaldisplaylink/update/targetpresentationtimestamp)). The review found v3 clamped an expired render deadline to callback time, allowing a late opportunity through scheduler eligibility. The host source now passes the raw deadline and counts expired callbacks. A corrected-source v4 run lasted 61.014 seconds: 1,760 source updates (28.846/s), 3,573 callbacks (58.560/s), 1,683 submitted/ready blends, 1,678 selected G, 3,569 timestamped presentations, three zero-`presentedTime` outcomes, 50 scheduler deadline misses, and 81 dropped generated opportunities. No callback arrived after its raw render deadline, so late-callback rejection was not exercised. The native actual-minus-target offset was 68.834 μs p50 and 16.713209 ms p95; 242 of 3,569 timestamped presentations were more than 8.33 ms after the native target. G was presented 83.272 ms p50 after its source-pair midpoint and 49.938 ms p50 after the callback-time scheduler target. Review of pair timestamps found 466/1,678 G outputs bracketed by presentations of their exact source pair, but only 144 immediate A→G→B and 142 immediate B→G→A triplets matched that same pair. Other selections repeat or regress source IDs (for example, B2, then G from source pair 2→3, then B2 again); this shows intermittent pair-correct sequences, not sustained source-aligned 2x cadence. Apple's [`presentedTime`](https://developer.apple.com/documentation/metal/mtldrawable/presentedtime) is zero when a drawable is not yet presented or was dropped, so the three v4 zero-time outcomes cannot be classified more narrowly from that property alone. No run inspected visual scanout. See the [synthetic-host notes](../../experiments/dxmt_framegen/evidence/step10b/README.md), [v4 CSV](../../experiments/dxmt_framegen/evidence/step10b/arm64-v4/synthetic-display.csv), and [all retained Step 10B captures](../../experiments/dxmt_framegen/evidence/step10b/).

These experiments did not import a DXMT source texture, call DXMT's `Presenter`, verify application DXGI Present/buffer progression, or exercise a Wine x86_64 Framegen path. A bounded mailbox polled only by D3D12 `Present1` cannot produce a refresh while application Presents are idle; at 30 source Presents/s it cannot supply the 60 display opportunities. When B arrives, G(A,B) is too late for an earlier callback unless B is deferred. A valid route therefore needs a display-tick-owned presentation path, retained/copied source history, native resource import, ordered G then B on later display opportunities, and explicit DXGI latency/Present-return/lifecycle handling. That is a multi-subsystem pipeline, not a safe mailbox-only patch; no downstream DXMT integration patch was produced. This path appears implementable in principle, but the required ownership and recovery contract has not been implemented or validated. No resize/focus/lifecycle matrix, multiple-swapchain test, injected-failure matrix, Metal HUD comparison, 15–30 minute soak, or RIFE run was performed.

The source-grounded prototype boundary is: WineMetal's native DisplayLink callback retains a typed drawable and signals a Wine event; one per-swapchain worker owns Presenter calls and consumes display ticks; `Present1` GPU-copies/enqueues each accepted source into bounded history and increments the DXGI-facing count once; after B is accepted, the worker submits G(A,B) and then B on separate display ticks. The worker must serialize with resize/layer changes and stop/join before teardown. DXGI frame-latency signaling must follow the eventual source-output lifecycle. None of these contracts has been coded or verified.

## Highball packaging implications and recommended next step

No supported DXMT extension point for an external frame-generation library was found, and the supported cross-build is not runtime integration. A downstream DXMT change may be required, but its scope is larger than a small packaging patch because it needs a display-tick-owned presenter and native/Wine Metal resource bridge. Treat that as an unvalidated implementation direction, not a Highball design. Keep Framegen as a separately replaceable runtime library, place its model file outside the DXMT source/binary component, and expose a distinct `FRAMEGEN_DXMT_*` configuration/capability surface only after the renderer path is validated. Do not use LSFG-compatible variable names. Capability detection should report the Metal device, display timing path, supported source formats/color space, and selected presenter; unsupported or secondary targets should remain on normal DXMT presentation.

**Recommended next step:** continue only with a version-pinned local downstream prototype of the complete display-tick-owned DXMT presenter, including deferred-source/backbuffer ownership and native Framegen texture/event bridging. Review DXGI-facing Present and frame-latency semantics before running the controlled 30→60 app. The accepted result must prove A/G/B order from source-pair IDs, actual presentation timing, resize/focus/teardown behavior, fail-open recovery, and unchanged app progression. Do not connect RIFE or alter Highball until that path passes.
